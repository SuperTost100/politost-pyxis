# Security

## Report a problem

Don't describe a vulnerability in a public issue. Report it privately through GitHub: open the repository's Security tab and choose [Report a vulnerability](https://github.com/SuperTost100/politost-pyxis/security/advisories/new). Only the maintainer sees the report.

Include the version shown in Settings → About, the operating system, reproduction steps and a minimal example made from invented content. Do not include API keys, provider authentication files, real source passages or your workspace database.

## Local storage

Electron stores app configuration under its OS-specific `userData` directory. Its default name is `politost-pyxis`; the exact workspace path is shown in Settings. `config.json` records a moved workspace. The workspace contains SQLite `pyxis.db`, content-addressed blobs, downloaded runtimes and local model files. Study data is not encrypted at rest by Pyxis. Use OS disk encryption if needed.

API keys are encrypted with Electron `safeStorage` and stored in `userData/keys.json`, outside the workspace. Main decrypts them for the core provider adapter; renderer queries cannot read the key file. Linux refuses key storage when only the plaintext `basic_text` backend is available. Main opens the OS key store only when `keys.json` holds a key, or when a key is saved. On macOS that store is the login Keychain, and reading it from a build the Keychain doesn't trust asks for the account password; a student without API keys never sees that prompt. CLI-provider credentials belong to the CLI and its authentication system.

The crash-report switch is stored in the workspace with the profile. Main keeps a copy, the queue of JavaScript error reports waiting to be sent, and the fingerprints sent today in `userData/crash-reports.json`. Crashpad writes minidumps to `userData/Crashpad` on Linux and to the platform's crash-dump folder elsewhere; while the switch is off, Pyxis deletes them at the next start without sending them.

Automatic backups are on by default. Once a day while the app is open, main writes `pyxis-auto-backup-<date>-<time>.zip` to `Pyxis backups` in the Documents folder, or to the folder chosen in Settings > Data, and deletes older files with exactly that name pattern beyond the newest three. It never deletes other files in that folder or manual backups. A folder inside the workspace or inside `userData` is refused. The setting, the folder and the last result live in `userData/backups.json`, outside the workspace.

Workspace backups include the study database and source blobs. They omit API keys, downloaded runtime/model caches, scratch files and the exports folder. Restore keeps runtime/model caches already present on the destination computer. Plan exports omit progress unless selected, but include saved study content and cited source excerpts. Embedding original sources requires a separate export choice. The plan export dialog also offers a profile-name choice for its author metadata. A calendar file (`.ics`) holds one plan's title, subject and exam date. Treat backups, PDFs, Anki decks, calendar files and shared plans as private documents when their content is private.

An update download accepts only `https://github.com/<repository>/releases/download/...` URLs of the repository in `package.json`, and follows redirects only to `release-assets.githubusercontent.com` or `objects.githubusercontent.com` over HTTPS. It refuses prereleases, a release that is not newer than the installed version, and installers over 1 GiB. The installer streams to `userData/updates`; Pyxis keeps it only if its size equals the size GitHub lists and its SHA-256 equals the release's `SHA256SUMS` line, and deletes it on a mismatch, a failure or Cancel. That folder is emptied at every start. An AppImage or a Mac zip can instead be rebuilt from the previous file: blocks it already has are copied from the running `$APPIMAGE` or from the zip kept in `userData/update-base`, and the others come as HTTP Range requests for the same asset, through the same URL and redirect checks. The new blockmap comes from the same release (embedded at the end of the AppImage, or the zip's `.blockmap` asset). The rebuilt file must pass the same size and `SHA256SUMS` check; a missing or unreadable blockmap, a server that ignores Range, or a mismatch makes Pyxis download the whole file instead. The hand-over never runs a shell or administrator command: macOS unpacks the zip with `ditto` and shows the app next to a link to Applications (or opens the disk image when the release has no zip), Windows starts the installer by its full path once Pyxis quits, an AppImage is copied next to `$APPIMAGE`, checked again, made executable and renamed over the old file, and a `.deb` is shown in its folder. Pyxis closes for an update only when no backup, restore, move or wipe is running, and asks first when background tasks are running.

Known limits of that check: `SHA256SUMS` comes over HTTPS from the same GitHub release as the installer, so it catches a damaged or swapped download but not a release that was itself tampered with. The builds carry no Developer ID or Authenticode signature for the OS to check, and Pyxis does not verify the build attestation. `gh attestation verify` remains the manual check for that.

Importing a photo uses the selected vision engine when it supports images, after the provider acknowledgement. This sends the image pixels to that provider; HEIC/HEIF is decoded to PNG first. With no vision engine, OCR is local, and so is the OCR of a scanned PDF page and of a chat photo. Local OCR needs the English and Italian language data above. Nothing downloads it until the student agrees: the agreement is a stored setting, the download is a visible job that can be cancelled and retried, and no code path fetches it otherwise. Until then every OCR path refuses with a message that says the data is missing, and a file whose hash no longer matches is refused the same way. tesseract.js is given only a private local folder holding the verified bytes, with its cache and its default CDN source switched off. A vision failure falls back to local OCR and records that path; cancellation or declining disclosure stops the import.

Prompts for tutor replies and generated study material include profile data the student entered. The chat system prompt carries the education level (a plan's own level when the chat belongs to a plan), the year, school and course if filled in, and the interests line when its switch is on; lessons add school and course, and exercises, quizzes, cards and mock exams add the interests line. These leave the computer to the selected provider with the rest of the prompt. The display name is not sent in any prompt; it stays local, apart from the optional author field of an exported plan.

Pyxis has no account server or telemetry service. Crash reports are the one diagnostic upload, and they leave only while the crash-report switch is on. It is off for a new profile and for an install that never saw it. The student turns it on in setup or in Settings > Privacy and can turn it off there at any time, without a restart. A JavaScript error report holds the app and Electron versions, the OS, the CPU architecture, the process kind and the error's name, message and stack. Main scrubs it first: the home folder, workspace and `userData` paths and everything after them, other absolute paths, URLs, quoted text that is not clearly code (a plain word such as a name goes), API keys, tokens and e-mail addresses are removed. A minidump is written by Crashpad and sent unchanged. It holds thread stacks, the loaded modules with their paths (which can include the account name) and some memory of the crashed process, which can hold fragments of what was on screen, as the switch's copy says. Nothing is sent before core has read the switch from the profile in the current session: Crashpad starts with uploads off, and JavaScript errors wait in memory. An error raised or a dump written while the switch is off is never sent later: the error is dropped at once, turning the switch off empties the queue, and the dumps are deleted at the next start before Crashpad runs. The Worker keeps no IP address, no request headers and no installation id. It uses the address only as an in-memory rate-limit key, and reports are deleted after 90 days by an R2 lifecycle rule on the bucket and, in case that rule is missing, by the Worker's own daily sweep. [Crash reports](docs/crash-reports.md) has the details and the limits of the scrubbing. Do not interpret the switch as consent for provider uploads; model requests use the engine selected for the feature.

## Boundaries

The renderer has context isolation, sandboxing and no Node integration. The main window's CSP, sent as a header and repeated in the built page, runs only the app's own scripts with no string `eval`, and loads images only from the app, `data:`, `blob:` and `pyxis-blob:`. Markdown in a shared plan or a model reply therefore can't load a remote image. Packaged builds set Electron fuses so that another process can't run the app as Node, pass it `NODE_OPTIONS` or attach a debugger with `--inspect`. They load the app only from `app.asar`, which macOS and Windows check against a hash embedded in the build. Shared IPC schemas validate requests before core handlers execute them. Main owns dialogs, OS key storage, protocol handlers and artifact writes. Print requests use a separate sandboxed window and sender checks. Python uses a fresh worker, bounded output, an interrupt timeout and restricted runtime requests.

Documents are read in a worker thread, never on the core thread: library imports, re-extraction and chat attachments (15 MB each, read within that cap and cancellable, with a two-minute limit for a chat file). A .docx, .pptx or smartbook archive is read through a bounded reader that counts the bytes it really inflates (64 MiB for one entry, 128 MiB for a .docx or .pptx and 256 MiB for a smartbook, taken together), whatever the headers claim, and does not inflate entries it does not need. The worker's JavaScript heap is capped at 2 GiB. Known limits: that cap covers the V8 heap only, so buffers, WebAssembly memory and native decoders (PDF stream decoding in pdf.js, the HEIC decoder, the OCR engine) are bounded by the file-size caps and by cancellation, not by the heap cap; a crafted PDF or image can still make a worker use a lot of memory or time until it is cancelled or the operating system stops it, which ends only that worker. ZIP64 and encrypted archives are refused.

These controls reduce accidental access; they do not make model answers trustworthy. Check generated citations and mathematical results, especially before using them in graded work. Never add source text, prompts or authentication material to diagnostic logs.

Restore checks database integrity, foreign keys and supported schema versions before swapping data. It retains the previous workspace until the replacement core is ready. A sibling journal supports recovery after interruption; mismatched directory identities stop recovery instead of deleting unrelated data. Keep any recovery copies until the owner has inspected them.

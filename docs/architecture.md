# Architecture

Pyxis is an Electron app with a React renderer, a privileged main process and a Node utility process for core work.

```text
                         OS dialogs, safeStorage, downloads
                                      |
renderer -- preload bridge --------> main
    |                                 |
    | MessagePort                     | utilityProcess parentPort
    v                                 v
   core <------------------------ startup/keys/workspace handshakes
    |
    +-- SQLite + sqlite-vec + content-addressed blobs
    +-- durable jobs + source/model workers
    +-- cli-funnel -> selected model provider

isolated Python renderer -> fresh Pyodide worker -> MEMFS
sandboxed print renderer -> main printToPDF -> chosen save path
```

Main creates the default `userData/workspace`, records its path in `userData/config.json`, and starts core. It writes `config.json` through a flushed temporary file, so a power cut leaves the old path or the new one. A `config.json` that exists but can't be read stops at the "can't find its data folder" dialog instead of opening the default workspace, which could hide a moved one. Main owns the BrowserWindow, CSP, `safeStorage`, native dialogs, backup/restore coordination, workspace moves and `pyxis-blob:`/runtime protocols. The built renderer loads from `pyxis-app://app/index.html` rather than `file://`, because Chromium keeps a V8 code cache only for schemes registered with `codeCache`. Later launches skip most of the script compiling. That handler serves only regular files inside `out/renderer` and sends the window CSP from `src/main/csp.ts` with each one. On the first launch after the update, main copies every `file://` localStorage key the new origin lacks, such as the interface language and dismissed notices, and records the copy in `userData/storage-carried.json` so it runs once. The protocol handlers resolve the current workspace on every request, including after a move. A workspace move stops core, verifies a staged copy, commits the path, then starts the replacement core before removing the original. Automatic backups run in a worker thread while core keeps running; a manual backup, restore, move or wipe stops a running one first. See [automatic backups](data-model.md#automatic-backups).

The application menu is built in `src/main/menu.ts` for every platform and build; development builds add reload and developer tools. Menu text lives in main, in Italian and English. The renderer reports its interface language through `setMenuLanguage`, and main rebuilds the menu when it changes. A menu pick sends one command from the list in `src/shared/menu.ts` to the renderer, and the preload drops anything not on that list. `MenuCommands` in the renderer runs the command through the router, but only if `menu-guard.ts` allows it: not during onboarding, with a dialog open, while a page holds a lock (`useMenuLock` in `menu-state.ts`, used by quizzes, simulations, the plan wizard and setup), or while focus is in a text field whose text would be lost. The Ask composer is exempt because it keeps a draft per chat. Help > Keyboard shortcuts opens a dialog that is the one list of every shortcut; add a key to a page and to that list together. A new page for the Go menu is one entry in `goPages` plus its labels.

Electron gives a page no right-click menu, so main builds the one for text (`textMenuTemplate` in `src/main/menu.ts`) from the window's `context-menu` event, in the interface language: Annulla, Ripeti, Taglia, Copia, Incolla and Seleziona tutto in an editable field, each on only when the field allows it, spelling suggestions with "Aggiungi al dizionario", and Copia on selected text elsewhere. Its items are roles and the two spelling actions in main, so the page sends nothing. The window's own item menus prevent the page's `contextmenu`, and Chromium then sends main no event, so the two menus never both open. Spellcheck is on, as Electron's default, in the computer's language. `src/main/spellcheck.ts` can point it at the app's language and the other one the app ships (`it-IT` and `en-US`, on Windows and Linux; macOS's own checker chooses), at start and when the interface language changes, but `SPELLCHECK_FOLLOWS_APP_LANGUAGE` is off: Chromium downloads each dictionary from `redirector.gvt1.com` on first use (one file per language, once per profile), and that request is not in SECURITY.md until the owner allows it.

A `.pyxis` plan file that the system opens with Pyxis, or a second launch passes, is queued in main (`open-file` on macOS, the file argument and `second-instance` elsewhere). Main checks its name, type and size and reads it only when the renderer calls `openedPlan.take`; the renderer never passes a path. `OpenedPlans` in the renderer also takes a file dropped on the window, and sends both to the shared-plan page under the same guard as menu commands. See `src/main/plan-open.ts` and "Opening and importing" in `plan-file.md`.

Core owns `pyxis.db`, blob storage and domain handlers. `src/shared/ipc.ts` defines request, response and event shapes. Core parses inputs with Zod before dispatching. Errors use `{ code, messageKey, params, detail }`. `src/shared/bridge.ts` describes privileged main/preload operations separately.

Main transfers a fresh message port between core and renderer. React Query handles renderer request state and invalidation. The exam list, plan and Progress queries stay fresh for 30 s; a finished job or the `plans.evidence` broadcast marks them stale sooner. A job update refreshes only what its kind changes: the sources for an import, the build progress for a plan build, the download state for a download. Plans refresh when a job ends. Updates less than 250 ms apart refresh together. Streams have cancellation; job updates arrive as events. If core exits, main restarts it and transfers a new port. In-flight requests reject with `core-restarted` so the renderer can show the failure and reconnect.

## Storage and jobs

SQLite uses WAL with `synchronous = NORMAL`, foreign keys and numbered transactional migrations. Main stops core by message, and core checkpoints the WAL and closes the database before it exits. Passages have an FTS index and optional local embeddings in sqlite-vec. Source bytes live in content-addressed blobs. Extraction creates immutable document versions; citations retain passage IDs and locator metadata. See [data model](data-model.md).

`src/core/jobs/runner.ts` stores jobs and named steps in SQLite. A successful step stores its output before the next step. Retry preserves completed steps; cancellation aborts the active work. Startup changes unfinished running work to interrupted so it can resume. Imports, indexing and the OCR and search-model downloads resume on their own when their next step is local work (`resumeLocal`), once per step, so a step that keeps ending the process waits for the student. A step that calls a model, such as a photo's vision read, waits for Resume. An import resumed in its index step leaves its source ready while the vectors are redone. A step an update retired stays registered with `retired: true`, so a job saved before the update can still finish it. New jobs leave it out. Source imports, plan creation, generation and simulation grading register feature-specific step handlers. Some short operations are direct IPC requests.

"Ferma tutte" in Attività calls `jobs.stopAll`, which cancels every queued and running job except the work a page does itself, with no confirmation. The stopped jobs wait under "C'è bisogno di te" as one item, and its Riprendi calls `jobs.resumeAll`, which queues them again from the step each had reached, in the order they were made. A kind can name the request a job came from (`group` in its `JobSpec`, `JobView.group`): an import names its linked folder (`folderId`) or the Library batch it came with, and the index checks a plan change queues share one batch. The list shows the jobs of one kind and one request as one row from two jobs up, and `JobView.group.waiting` counts the folder's files not queued yet, so the row reads "Leggo le fonti · 12 di 37".

Image imports use the selected vision engine when its model supports images, with the same provider acknowledgement as other generation (confirmed at setup, in Settings or once at launch; a task never waits for it, and automatic selection skips an engine that is not acknowledged). Otherwise they use local OCR, which reads English and Italian `tessdata_fast` files pinned to one tesseract-ocr commit (`src/core/sources/ocr-data.ts`). Pyxis downloads them by itself once setup is done, as the `ocr-data-download` job in Attività (one step per language, so it shows progress, and it can be cancelled and retried): the shell asks core for it at each start (`sources.ocrDataAuto`), which does nothing when the files are ready and replaces a download that stopped. A screen that needs the data starts it the same way if nothing is downloading it. End-to-end runs download only from the local server that `PYXIS_E2E_OCR_BASE` names. Every OCR run reads them back, checks size and SHA-256, and gives tesseract.js a private local folder of exactly those bytes, so the library's CDN default and its cache are never used. Without the data, a photo import, a chat photo, a scanned-PDF page and a HEIC fail by name (`ocr-data-missing`, or `ocr-data-integrity` for an altered file) before any row or page is queued. The requests are `sources.ocrDataState`, `sources.ocrDataAuto` and `sources.ocrData`.

A scanned PDF (no text layer) is read by the `source-ocr` job in core (`src/core/sources/ocr-job.ts`). An extract worker draws 8 pages at a time with pdf.js and `@napi-rs/canvas`, then reads them with Tesseract. Core stores each page as it comes back and moves the job's progress. Core's main thread keeps the canvas addon loaded, so a worker that stops cannot leave the addon's thread behind on Windows. The window only watches the job, so leaving the Library, reloading or closing the window does not stop it. A quit leaves the job interrupted with its pages kept, and the next start resumes it from the first page without text. A run that dies again before storing a page waits for the student's Resume instead. The job starts by itself after an import that turns out to be a scan, and when the OCR data download finishes, unless the student turned the download off. Otherwise the Library and the exam wizard offer "Read the scan" (`sources.ocr`). Stop, a failure, or a replaced file puts the scan back to `needs-ocr`, keeping the pages read.

Failed vision extraction falls back to OCR, while cancellation or declined disclosure stops the job. Original HEIC/HEIF bytes stay in the blob store; decoded PNG pixels go to vision or OCR in a worker. The document records its extraction path, actual model and versioned prompt. Native file drops resolve real `File` objects in preload and receive the same bounded file grants as picker imports.

Material comes into the Library once. `enqueueSourceData` looks the content up before it stores anything: the SHA-256 of the bytes for a file or pasted text, the web address for a link. A usable Library source that already holds it (not removed, failed, cancelled or interrupted) is returned and no job starts, whichever way the material came in. The lookup covers a file a linked folder reads in place, through the `content_hash` on its `linked_files` row while the file is present (an index on that column keeps the lookup short when a scan asks for thousands of files). A copy that a chat or a plan file keeps out of the Library (`library = 0`) does not count, because it goes with that chat or plan: importing the same file makes the Library its own source, and deleting the chat leaves that source alone. Nothing awaits between the lookup and the insert, so a file chosen twice in one request, or again while its first import is still queued or being read, ends as one source. Core throws `SourceExists` and the `sources.import`, `sources.paste` and `sources.link` handlers answer with that source and `existing: true`; the Library says "Già in libreria: uso quella." and selects it. Replacing a source's file (`existingId`) is not checked, since the student asked for that source to change.

A file, pasted text or link added from the Library page gets a subject chosen by Pyxis (`src/core/sources/library-subjects.ts`). The page passes `sort: true` with each import, which marks a new source `subject_sort = 'waiting'`, and then asks `sources.sortSubjects` once for the whole add, which starts one `library-sort` job, one row in Attività. Exam pages, chat attachments and plan files never ask, and linked folders keep their own sorting. The job first waits, holding no slot and for at most 90 seconds, until the files' first reading is over, so the AI tool sees what each is about; reading never waits for it. Then it calls `sortLibraryFiles` (`linked-subjects.ts`, prompt `library.sort`, the `default` feature), which shares its engine, time limit and error handling with the sorter of loose files in linked folders: 100 files a call with the subject names the student has, and each file with an `id` (its place in the call), its name and the first 400 characters of its text once read. The answer goes by `id`, so files with one title never share an answer, and a file the answer omits or names with an `id` that was not sent waits for the student. The job takes the subjects' ids before the call and resolves an answer through them, so a subject renamed meanwhile still receives its file, and one deleted meanwhile is not made again (the file waits for the student). The answer puts a file in one of those subjects, proposes a new subject (made once and shared by every file of the job given the same name, reusing a subject with that name in any case, also one the student made meanwhile), or leaves it to the student. A file Pyxis made a subject for is `created`, and its row says "Materia nuova" with Rinomina until that subject is renamed. A file left to the student is `unsure`, or `no-ai` without an AI tool, and waits in "Da sistemare" with a subject picker. Each file is written only while it is still `waiting`, so a choice the student made meanwhile stands, and a file the student placed (`manual`, from "Sposta in" or "Da sistemare") is never sorted again. A failed call fails the job with its files still waiting, which Riprova asks again; a stopped job leaves them in "Da sistemare" until Riprendi. A file read from a linked folder moves the same way, in Pyxis only: the file on disk stays where it is, the move marks its row as asked about (`sorted_at`), so the sort of loose files leaves it alone, and `manual` keeps setup again and a move on disk from changing it (see [linked folders](#linked-folders)).

A PowerPoint import adds each slide's speaker notes, found through the slide's relationships, to that slide's passage after the label `Speaker notes:`. A PDF locked with a password stops as `pdf-password-required` (or `pdf-password-wrong`). The student's answer goes to core with `sources.unlockPdf`, which keeps it in memory for the one read of that import and never in the job's input, so a retry or a resume after a restart asks again. A source saved from a link can be fetched again with `sources.refresh`: a changed page becomes the next extraction version of the same source, as a re-extract or a book update does, and older passages keep the copy they were read from.

Long extraction and embedding work runs in workers, so IPC stays responsive. The embedding model loads once in one embedding worker, which serves calls in order and releases the model after a minute without work. A search goes before waiting indexing batches. The worker thread stays up for the life of core, and a cancel stops inside it, because ONNX Runtime can abort the process when its thread is terminated or replaced (#58).

### Linked folders

A linked folder is one of the student's own folders that Pyxis reads in place (`src/core/sources/linked.ts`). Pyxis keeps the extracted text and the page index of each file, never a copy of it, and only reads: nothing creates, renames, moves or deletes anything inside the folder, and no temporary or sidecar file goes there. Setup links folders in one of two modes. In `root` mode the folder holds the student's whole study and each first-level subfolder is a subject; files at its top level stay without a subject, unless it has no subfolders with material, when the folder itself is the subject. In `subject` mode each folder picked is one subject, whatever its subfolders.

`sources.linkFolders` takes the paths main's folder picker or a drop granted. A folder dropped on setup's folder step reaches main through `grantDroppedFolders`, which, as for dropped files, reads the path from the real `File` in preload and grants only a directory. Core checks each against the folder grants at the IPC boundary, as a folder import is checked, and the handler then refuses a path that is not an absolute directory (`folder-missing`), one inside the workspace or the app's data (`folder-inside-data`), and one inside a linked folder or holding one (`folder-overlap`). A walk never enters the workspace or the app's data, so linking the home folder does not read Pyxis's own files.

A linked folder is read in full, with no cap on files. Hidden names and symlinks are skipped, so a link can never lead the walk into a cycle, and folders nested more than 32 levels deep are not opened (`MAX_LINKED_DEPTH`); the look records that cut, and one for a subfolder the system would not open, in `cut_json`, and setup says so. The walk (`walkImportable` in `folder.ts`) reads each folder through the thread pool a few entries at a time and lets the event loop go every 256 entries, so core keeps answering requests while it reads tens of thousands of files.

Linking does not wait for the full walk. It reads each first-level subfolder only up to 40 file names or 5,000 entries (`peekFolder`), enough to name its subjects, and returns at once; the full walk runs in the background. Subjects are named with one model call per 60 folders for all the folders a request links (`linked-subjects.ts`, prompt `folders.subjects`, the `default` feature). It sends the folder names and, for each, up to 40 file names relative to it, never a file's content. The answer, validated against a schema, tidies each name ("Fisica 1" becomes "Fisica I"), marks a folder that is not study material (in `root` mode only) and names the kinds of material: book, slides, exams, notes, exercises and handouts. Without a ready engine, or when the calls fail or take more than 60 seconds, the folder names are used as they are and nothing is skipped. Reading starts as soon as the folders are linked, for every subfolder that is not skipped. A subfolder whose material lay past the sample is found by the walk and named as the folder is.

Files lying loose at the top of a `root` folder that has subject subfolders are sorted into those subjects by name (prompt `folders.sort`), 100 names a call, after the walk records them. The model sees the subjects and the file names, never a file's content, and answers with the subfolder each file belongs to, or none. A sorted file takes that subfolder in `linked_files.subfolder`, so it follows that subject from then on, and `sorted_at` keeps it from being asked about again. Without an AI tool the loose files stay without a subject and a later look asks again; after a failed call a `linked-folder-sort` job asks once more, and when that fails too it ends as a failed job in Attività (`linked-sort-failed`) with the files still without a subject; the folder is not asked again until the next start, or until Riprova on that job. `sources.confirmFolders` then saves the names the student confirmed: each creates a subject or reuses the one with that name, and the subfolder's sources take it. A skipped subfolder marked as a subject is read then. A folder setup never confirmed gets the names it offered at the next start.

A look records each new file as a `linked_files` row with `pending = 1` and no source, in one transaction per batch of 256. A queue (`pump` in `linked.ts`) then hands recorded files to the job queue oldest first, only while fewer than 48 `source-import` jobs wait or run, every 400 ms. A folder of tens of thousands of files therefore never fills the job queue or the jobs list, and a restart carries on with the files still recorded as waiting: the queued imports resume, and the look at start finds every recorded file unchanged. A changed file waits the same way, as `pending = 2`. The queue leaves a folder's new files alone while its walk is running, because one of them may turn out to be a file that moved. It also leaves a folder alone while the student has some of its readings stopped, until they are resumed or cleared, so stopping them does not just hand over the next files. Each file becomes a source with no stored original (`blob_sha` is NULL) when the queue takes it, under its subfolder's subject at that moment. Its `source-import` job carries `linked: true` and reads the file from its real path in the extract worker, after checking that it is still a regular file inside the folder, and hashes it there for the row. A scanned PDF is read by the `source-ocr` job from the same path. Photos are read by local OCR only, never by a vision model, so a folder of photos does not spend the student's AI requests; until the OCR data is downloaded they are left unrecorded, and the download's end looks at every folder again.

Core looks at every linked folder again at each start and whenever the folder's watch sees a change: a recursive `fs.watch` that runs the look 2 seconds after the last event of a burst, or 20 seconds after the first while events keep coming, and that closes when core shuts down. A look after a watch reads only the places the burst named (a subfolder, or one file and the rows under its path), so a change in a folder of 50,000 files does not walk the other 49,999. A burst with an unnamed event, or more than 256 places, reads the whole folder. A look that lasts longer than a second shows in Attività as "Leggo la cartella: N file trovati" (`linked-folder-read`, through `Runner.track` with `keep: false`, so it leaves no finished job). A look compares each file's size and modification time with its row:

| What the look finds                                  | What happens                                                                                                                      |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| A new file                                           | A new source with its import job, under its subfolder's subject                                                                   |
| A file whose size or time changed                    | Hashed first. Same contents: only the row changes. Otherwise the next version is read                                             |
| A new file with the size and hash of one that's gone | A move: the row and its source follow the file, into another subject if it moved, unless the student chose its subject (`manual`) |
| A file no longer there                               | `missing_at` is set. The source, its text and its citations stay                                                                  |
| A missing file that's back                           | `missing_at` is cleared                                                                                                           |
| The whole folder gone                                | Every file is missing until the folder is back                                                                                    |

The Library shows the subjects the student has, and the student can change them there. A subject renamed in the Library keeps its id, which `linked_subfolders.subject_id` holds, so a later look files new files under the new name and never makes a subject with the old one. Only a subject that nothing has (no Library file, exam, map, flashcard or chat) can be deleted from the Library (`subjects.remove` with `onlyEmpty`). Deleting it clears the subject of the subfolders that named it, which stay linked without one: a later look does not make the subject again, and new files in that subfolder wait in "Da sistemare". Setup again can give the subfolder a subject once more.

A look that marks a file missing, finds one again or follows a move sends the `sources.changed` broadcast, so the Library reads its list again; new and changed files are announced by their jobs. A walk that the depth cap cut, or that met an unreadable subfolder, marks nothing missing, because it cannot tell a file that is gone from one it did not reach. A changed file whose source has an unfinished job waits for the next look. A new version is published as a re-read is: older passages stay and the items that cite them are marked stale. A source the student removed from the Library is not read again, and a deleted one leaves its row with a NULL `source_id` for the same reason. A new file with the same bytes as a file imported into the Library earlier takes over that copy instead of making a second source. A look hashes the new files whose size matches a stored original, as it does for moves, and points the file's row at the copy, so the Library shows it once with its text, versions and citations as they were, and nothing is read again. The copy takes the subfolder's subject when it has none and keeps its own otherwise, also when setup is confirmed later. A subject it took from the folder follows the folder: when confirming gives the subfolder another subject, a copy with no subject or with the subfolder's previous one moves to the new one, and a copy with a subject of its own stays. It keeps its stored original, which it is read from while the file is unchanged (a scan's OCR included) and which keeps it in the subject's maps while the file is missing. Once the file changes, the next version is read from the folder and the source stops naming the original as its current file; the first version still names it, so the original stays stored. A copy kept out of the Library by a chat or a plan file, a link's page, a failed or removed import, a copy another linked file already took over and a copy being replaced with another file (its stored original is not the text it is about to hold) are not taken over, and files recorded before this look (such as at a restart) are read as their own sources. The Library shows a linked source's subject, and "Moved or deleted" for a missing file. The tables are in [data model](data-model.md).

The Library's head has one control for the linked folders, "3 cartelle collegate", which opens a list of them (`LinkedFolders.tsx`). Each folder shows how many files Pyxis reads there and how many of them are read (a file counts as read only when its reading ended with a usable source; `failed` counts the ones whose reading failed, was stopped or waits for the student, and the row says so and sends the student to Attività, where Riprova is, while the shelf marks those files), when the last look ended (`synced_at`), and whether a look or a reading is running or the folder is no longer on disk (`state` in `sources.linkedFolders`). Its menu has three actions:

| Action            | Call                        | What happens                                                                                                                                                                                   |
| ----------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mostra nel Finder | `revealLinkedFolder` (main) | The window sends only the folder's id. Main asks core for that folder's path and opens it with `shell.openPath`, so a page can never have a path of its own choosing opened                    |
| Rileggi adesso    | `sources.rereadFolder`      | One full look at that folder, in the background, and its watch again if it had stopped. The list and Attività show it as any look                                                              |
| Scollega…         | `sources.unlinkFolder`      | After a confirmation, in one transaction: each of the folder's sources is removed as `sources.remove` removes one (`removeSource`), and the folder's row goes with its subfolder and file rows |

Unlinking removes what the folder brought and nothing else:

| What hung from the folder                         | After unlinking                                                                                                                                                                                                             |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Its files                                         | Marked `removed`: out of the Library, search, retrieval and every exam's material (`plan_sources`). Their passages stay                                                                                                     |
| A Library copy the folder took over               | Stays in the Library as an added file while its stored original is still its current file (`blob_sha` set and the blob present). A copy whose file changed in the folder reads the folder's text and leaves like the others |
| Its subjects                                      | Stay, even empty. The student deletes an empty one from the Library                                                                                                                                                         |
| Flashcards, maps, lessons and quizzes             | Stay, with the text they cite                                                                                                                                                                                               |
| Citations in answers and lessons                  | Stay. The source panel still shows the cited passage and says the source is no longer in the Library (state `removed` in `sources.panel`)                                                                                   |
| Its reading                                       | The look stops (it checks an abort signal between batches, so it writes nothing after), the watch closes, and every reading of its files is dropped from Attività (`Runner.discard`), so nothing offers to resume it        |
| Subfolder subjects, suggested kinds, file records | Deleted with the folder's row                                                                                                                                                                                               |
| The folder on disk                                | Untouched                                                                                                                                                                                                                   |

Linking the folder again reads it as new: its files become new sources, the removed ones stay removed for their citations, and a subject chosen by hand for one of its files before does not come back. A copy that stayed is taken over again, so nothing shows twice.

A folder that is no longer on disk shows "Trova la cartella…". The student picks where it went, through the folder picker's grant, and `sources.relocateFolder` takes it as the same folder when more than half of the files read from it are at the same relative path with the same size, counting only the files the folder's own walk would read there (regular files reached through real folders, never a link). Names and sizes are what Pyxis keeps of every file; a hash is kept only for some, and checking it would read every file. The folder then keeps its id, subjects and sources, and the look that follows finds its files again (a file copied with a new time is hashed and, with the same contents, only its row changes). Otherwise nothing changes, and the list says how many files matched and offers to link the picked folder as a new one.

### The source panel

The source panel shows a Library file at a page: from a cover, a row of an exam's material, or a citation in a chat, a lesson, a quiz's results, a map or a flashcard. `sources.panel` (`src/core/sources/panel.ts`) tells the window what it can draw: the file's type, whether its original can be read now (the copy Pyxis stores, or the linked file read in place), where its read is (`ready`, `reading`, `locked`, `failed`, `removed`), whether a linked file is missing, and the cited passage with its page. The window decides from that what to show (`components/sourcePanel.ts`): a PDF's page, an image, or the text Pyxis read laid out as a page for Word files, slides, plain text, saved web pages and free books.

A PDF is drawn by pdf.js in the window from bytes core reads on request (`sources.readOriginal`, at most 2 MiB a call). pdf.js asks for 64 KiB chunks and only for the ones the page it draws needs, so a 36 MB book of 900 pages opens at page 412 having read about 280 KB of it. A longer range, such as a large picture's stream, is read in pieces of at most 2 MiB. A read that fails ends the load: a file core reports as `source-file-missing` shows the panel's missing state (a linked file that moved, or a stored copy that is gone, each with its own words), and any other failure shows Riprova. The window keeps one picture of the page on screen and of the two seen before it, at the width drawn last, and lets go of the others. The request names the source or the passage by id, and core reads only that source's stored copy or its linked file, after checking that the linked file is still a regular file inside its folder. A citation keeps the version it was read from: an older version's own stored copy is read when it has one, with that version's kind (from its tree) and type (from the copy's own record), since a replacement can change both.

"Apri il file" asks main to open a source by its id (`openSourceFile`). Main asks core which file that is, and core answers only for a source still in the Library. A linked file opens in place. A stored copy is named by its hash with no extension, and the system picks the app by the extension, so main copies it to `userData/open-copies/<source id>/<hash>/<file name>` first and the system's app opens the copy (`src/main/open-copies.ts`). The folders are the record of the copies, so a run that crashed leaves nothing main can't find. A copy goes when core no longer has that file in the Library: core tells main after a removal, an unlinked folder, a deleted chat, a finished job or a look that changed something (`library-changed`), and main asks core about each copy. All of them go before a wipe or a restore replaces the workspace, when the app quits and at the next start. A copy an app still holds open, which Windows refuses to delete, stays until one of the next tries. The window never names a path.

### Import limits

Core checks a file's size before it allocates a buffer for it. An import job reads its file in the extract worker, two at a time across all jobs; the next step stores the passages under the hash the file was queued with, without reading the file into core again.

| Input                     | Limit                                                     |
| ------------------------- | --------------------------------------------------------- |
| Document import           | 256 MB                                                    |
| Photo import              | 40 MB                                                     |
| Chat attachment           | 15 MB, read in the extract worker with a two-minute limit |
| One ZIP entry             | 64 MiB inflated                                           |
| `.docx` or `.pptx`, total | 128 MiB inflated                                          |
| Smartbook, total          | 256 MiB inflated                                          |
| Folder import (a copy)    | 2,000 files, 12 levels deep, 20,000 entries read          |
| Linked folder             | No file cap, 32 levels deep                               |
| Extract worker heap       | 2 GiB of V8 heap                                          |

The IPC server reads the size from `fstat` and refuses a file that grows past its cap during the read. A chat document is read in the extract worker (`mode: "extract"`, behind the same two-at-a-time gate as photo decodes, and cancellable) from the bytes core already read, and core stores it in one transaction as a chat-only source.

Office files and smartbooks open through `src/core/sources/zip-bounded.ts`. It reads the central directory only for locations, inflates just the entries it needs in small pushes, and counts the real output, so a lying header or overlapping entries cannot exceed the caps. mammoth only ever sees a stored archive that the reader rebuilt from the XML parts.

The heap limit does not cover buffers, WebAssembly or native decoders (pdf.js stream decoding, HEIC, OCR). Those stay bounded by the size caps and by cancellation. Folder scans hash files by streaming in the extract worker. The blur check and its hash run in the same worker.

### Photos sent to a vision model

A photo goes to a vision model as a fitted copy: at most 1.5 MB of raw bytes and 2,560 px on the long edge, turned upright from EXIF, with transparency flattened onto white, and re-encoded as JPEG when it had to shrink. That keeps eight new and four saved images inside the 5 MB per image and 32 MB per request limits Anthropic documents. The stored original is untouched.

A chat keeps the fitted copy and the original as two attachment rows. The original's type carries an `;original` suffix so a resend never sends both. An imported photo's document records the size sent and what it was resized from. WebP has no decoder here, so an oversized WebP goes through local OCR instead.

### Lessons, quizzes and concurrency

Long-topic lessons cover every passage in consecutive calls with at most 24,000 characters of source text per call. Citation numbers stay stable across parts. The lesson prompt asks for about six sections (five to seven) and at most six quick checks in the whole lesson; each part of a long topic gets its share of that, so a long topic does not grow into a long lesson. While a lesson is written, the lesson page shows each section once the next heading has appeared and a status naming the section in progress, so the text a student is reading never moves. The combined lesson is cached only after all parts pass validation, so a failed rewrite preserves the previous lesson. Prepared model-written simulations retain questions without starting an attempt; an explicit Start starts the clock. A plan with past exams (`src/core/study/pastPapers.ts`) reads each one with a `paper-read` job, and the simulation builder then copies their question count, types and difficulty; the simulation setup lets the student choose the standard format instead. Quiz deadlines are enforced in core against the saved answer draft. A timed quiz takes no answers or checks until every question is written, and its clock starts at the first save after that. A graded attempt, its evidence and its path step carry the time its answers froze, at submit or at time-up, not the time grading finished.

A topic's lesson can also be written in short parts (`src/core/study/parts.ts`, `partJobs.ts`). Each part is written by a queued `lesson-part` job, which is `interactive` because the part ahead is needed while the student reads the one before. The job has two steps: `outline` plans the topic's parts when it has no live outline and does nothing otherwise, so a retry after a failed write keeps the saved outline, and `write` writes the part at the job's position. Each part call gets the whole outline, the headings and summary of every part already written, and only that part's passages. Each passage belongs to one part, so no two calls teach from the same material, and the whole request stays within the same 24,000 characters as a lesson call: source headings are cut to 200 characters, every passage keeps some of its own text, and the request's size is checked before the call. `partShape` checks the reply before anything is saved: it repairs a fence around the reply, a leading title, extra question blocks and the closing `pyxis-takeaway`, which becomes the part's summary. It asks once more, with one line per broken rule, when the part has the wrong number of sections, does not end with its question, is too short or too long, repeats a heading of another part, or has no usable takeaway. A second reply is saved when a page can show it, without its question if it has none, and otherwise the job fails with `lesson-part-invalid`. The part's lesson item, its summary and its measured minutes are saved in one transaction, so a cancel, an engine error, a missing engine or a quit leaves the outline and the earlier parts as they were. Every start goes through one function in one transaction: opening a part starts, resumes or retries that part's job, and opening a written part starts the part after it only when no part job of the topic is queued or running. A failed job ahead is left for the student, so a topic has at most one part written ahead of the one being read, plus the parts the student opened. `study.parts` lists a topic's parts, and `study.part` opens one, starts the part ahead, and reports `planning`, `writing`, `written`, `failed` or `book` (no engine set up: the part's passages as book text, not saved). A topic with a lesson written before parts opens in the existing reader. The Markdown export of a topic in parts joins its written parts in order and lists the sources those parts were written from.

Default limits are two CLI model jobs, four API model jobs, one demo job and `max(1, availableParallelism - 1)` local jobs. A job the student waits for on screen (checking a quiz answer, grading a quiz) is `interactive`: it counts only against other interactive jobs of its class, so it never queues behind a quiz being written or a mistake analysis, while background work still counts it. A topic quiz is written four questions per call and saved after each call, so the quiz screen's count of ready questions moves while the student answers. A lesson being written, a lesson section rewrite and flashcards suggested from a selection are calls the page makes itself; core lists them in the jobs list with `Runner.track` while they run (without a cancel, since their page stops them) and keeps the ones that succeed as finished jobs. A plan build writes its introduction and its diagnostic in one step that holds one CLI slot and makes both calls at once. Each result is saved as it arrives, so a failed call keeps the other and a retry asks only for the missing one.

Python runs in a separate sandboxed renderer/worker context with local Pyodide, SymPy and MEMFS. A fresh worker isolates each run. The configured timeout interrupts execution and a hard timeout terminates it. It cannot read the Electron workspace through Node. Grading uses the same SymPy worker as the Ask checks (`check_grade` in `src/sandbox/symbolic.py`). For a math answer it compares the student's final answer with the reference (expressions, equations, solution sets and intervals) and finds the first step of a worked solution that does not follow from the one before. Core sends the verdict to the grading model as `mathCheck`, and credits a fill-in blank that is the same mathematics as an accepted answer. Grading waits at most 12 s for the check, and without the downloaded runtime, or when SymPy cannot read the text, it grades as before. Lessons and Ask answers can ask for a figure as matplotlib code in a `pyxis-figure` block, when the runtime is downloaded. Core runs each figure's code there once, with an 8-second limit and at most 4,000 characters, and stores the PNG with the lesson or message; a figure that fails is removed and the rest is saved. PDF export renders sanitized Markdown and KaTeX in a separate print window, waits for readiness, then asks Chromium for an A4 PDF. A concept map's PDF also carries the SVG that `maps.export` draws in core. The print page shows it as an image on a first page sized to the drawing, then the outline follows on A4.

### Concept maps

A concept map belongs to a subject, and optionally to one topic of an exam (`src/core/maps/`). Every map request names a topic (`topicId`, with or without its `planId`) or a subject alone (`subjectId`), and `mapScope` turns that into the row it means; a topic's exam and subject come from the topic. A topic map is built from the topic's passages, read in parts of at most 24 passages and 18,000 characters. The parts of one request join into a single map (`merge.ts`): its root is the topic's name, and each part's root becomes a main branch under it. The prompt tells the model the topic's title and which part of how many it is reading, and has it label the root of each part with a short name of its own for what that part covers. A part root that repeats the title (ignoring case and the spaces around it) folds into the map's root, parts that return the same root label share one branch, and a concept two parts name alike is kept once, with the sources of both. Each finished part waits in the job's params until the last one is read, so a resumed or retried build reads only the parts it has not read, and no half-built map shows. A map holds up to 2,000 concepts (`MAP_LIMITS`); a map of more than 25 opens with everything below its main branches folded. The view moves on its own (when the map opens and after an unfold) only down to a zoom of 0.85 (`MIN_READ_ZOOM`), which keeps a concept's label at 11 px or more on screen at every text size. The opening view shows the whole visible map when it fits at that zoom, else the root and its nearest branches, and an unfold puts the branch's parent and first children on screen and leaves the rest to scrolling. The student can still zoom out by hand. The Nuova mappa dialog opens the map page with `build` in the navigation state, and the page starts the build once it has found no map and no build for the scope. The dialog also lets the student say how they want the map (up to `MAP_INSTRUCTION_MAX`, 2,000 characters, as for `maps.edit`). `maps.generate` takes it as `instruction`, trimmed, and an empty one is none. It is kept in the job's params, so a retry or resume sends it again, goes to every part's call as `instruction`, and is stored in the map's own JSON (`StoredMap.instruction`, no column), where the Mappe tiles and the switcher beside the map's title show it. The prompt (`map.generate`, version 6) takes it as guidance about focus and style that never overrides grounding, the schema or the content language. With one a map need not cite every passage and may be as small as two concepts, and a part that holds nothing for the request answers `{"result": {"kind": "nothing"}}` instead of a map (a request without an instruction keeps the plain schema, at least eight concepts per part). Such parts are done like the others, so a resume or retry does not read them again, and they stay out when the parts join. When every part is empty no map is stored and the build fails with `map-nothing-matched`, which the map page shows with the request in a field the student can change. That error is in `EMPTY_RESULT_ERRORS` (`src/shared/ipc.ts`), so Attività lists the build with the jobs that ended today, not as a problem, and its row opens the map page on that build: the navigation state carries the job's id, since a scope can have several such requests, and the page shows that request's words in the field even when the scope already has maps (the switcher beside the title then lists them, also when there is only one). The id stays in that history entry, so a reload or Back and Forward return to the request, and a request whose job is gone, or anything the student does on the page, takes it out. A request without an instruction gets the scope's map or its build as before. A request with one is a map of its own: a finished build does not answer it, so the map is added next to the others, and only a build that is queued or running for the same scope and the same instruction is the same request (`enqueueMaps`). While such a map builds, the page shows its working state in place of the maps already there and opens the new map when it is done. The page reads the build it waits for by job id (`maps.build` takes the `jobId` that `maps.generate` returned, and falls back to the scope's newest build when the page opened without a request), and opens the map by the `mapId` the finished build returns, since two builds of one scope can finish in either order. A whole-subject map is one map from one call: up to 24 passages of the subject's sources, each cut to 750 characters (`subject-sources.ts`). Those sources are the subject's files in linked folders, the material imported with the subject and the study material of the subject's exams, at their newest version. Hidden copies, files gone from their folder, sources still being read and past exam papers that none of the subject's exams studies from stay out. The first passage of each section goes first, spread evenly from the first section to the last when there are more than fit, and the rest is filled evenly from the other passages. Core reads the ids of all the subject's passages and the text of the chosen ones only. The model writes in the profile's content language, since no exam sets one. `maps.rename` gives one map a name of its own, which may repeat another map's, and keeps its request. `maps.delete` removes one map, with its undo history, and the row goes with its scope's last map. It also stops every build that writes that map (`Runner.discard`, which cancels the job and drops it from Attività so nothing offers to resume it), and a running build checks its signal right before it stores the map, so a build that ends later never brings it back. A map still being written has no id on the page yet, so the page names it by its build's `jobId`. A plain request whose finished build made a map that was deleted since starts a new build. Flashcards made from a map belong to the subject and stay, and a link to a deleted map (`?map=` in the address) lands on Mappe, which says the map was deleted.

The map page lives at `/maps/:subjectId` for a whole subject and `/maps/:subjectId/:topicId` for a topic. The older `/plans/:planId/map/:topicId` opens the same page, for links made before and for a topic whose exam has no subject. A concept's source opens in a side panel on the map page, at the passage it cites, with the same viewer the Library's drawer uses (`useSourceView` in `SourceViewer.tsx`); the canvas narrows beside it.

## Build and tests

Electron Vite builds main, preload, core and renderer entries into `out/`. Only the shell and the exam list are in the renderer's entry chunk; every other page loads on its first visit, and the previous page stays on screen until it has. A page with tabs or an optional id is therefore one route (`plans/:planId/:view?`), so its tabs switch without a load, and a redirect is a route loader rather than a rendered `<Navigate>`, which would cancel a navigation still loading its page. A stylesheet goes with the component that uses it, since a page's CSS now loads only with that page. Main and core load the HTML parsers (linkedom, Readability, Turndown) and mammoth on the first import that needs them. `electron-builder.yml` packages native libraries outside ASAR and chooses DMG/ZIP, NSIS or AppImage/deb. `scripts/test-electron.mjs` runs Vitest with Electron's Node ABI. Native Playwright tests launch temporary Electron profiles, rather than the owner's current workspace.

## Restore safety

Restore validates SQLite integrity and foreign-key references before and after migrations. Future schema versions and unexpected ZIP paths are rejected before live data moves. Only canonical hash-named blob files and their metadata accompany the database; restore verifies their hashes and metadata. Existing runtime/model caches are copied into staging and survive both commit and rollback. A fsynced sibling restore journal records the original and staged directory identities. Startup checks that journal before creating workspace folders.

The app keeps the original `.old` workspace until the restored core reports healthy readiness. The archive worker validates the promoted database, then commits and cleans up the swap, so this work stays off the main window thread. A commit that fails (a full disk, or a journal file Windows keeps locked) is tried twice more. After that, main stops core and tries once more, since a stopped core has let go of its files. If that fails too, main rolls back to the original at once, and Settings says the data from before the restore is back. If core won't stop or the rollback fails, core stays stopped, no backup, restore, move or wipe can start, and Settings asks the student to reopen Pyxis so startup recovery can finish. Core never keeps running on a promoted copy that the next launch would roll back and delete. An interrupted uncommitted swap rolls back to that original. Commitment is recorded before deleting old data; a failed cleanup leaves the committed marker for the next startup and never selects a partly deleted original. A replaced or unexpected directory stops recovery with both copies preserved for inspection.

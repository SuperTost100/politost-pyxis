# Architecture

Pyxis is an Electron app with a React renderer, a privileged main process and a Node utility process for core work.

```text
                         OS dialogs, safeStorage, downloads
                                      |
renderer -- preload bridge --------> main
    |                                 |
    | MessagePort                     | utilityProcess parentPort
    v                                 v
   core <------------------------ startup/keys/workspace handshakes
    |
    +-- SQLite + sqlite-vec + content-addressed blobs
    +-- durable jobs + source/model workers
    +-- cli-funnel -> selected model provider

isolated Python renderer -> fresh Pyodide worker -> MEMFS
sandboxed print renderer -> main printToPDF -> chosen save path
```

Main creates the default `userData/workspace`, records its path in `userData/config.json`, and starts core. It writes `config.json` through a flushed temporary file, so a power cut leaves the old path or the new one. A `config.json` that exists but can't be read stops at the "can't find its data folder" dialog instead of opening the default workspace, which could hide a moved one. Main owns the BrowserWindow, CSP, `safeStorage`, native dialogs, backup/restore coordination, workspace moves and `pyxis-blob:`/runtime protocols. The built renderer loads from `pyxis-app://app/index.html` rather than `file://`, because Chromium keeps a V8 code cache only for schemes registered with `codeCache`. Later launches skip most of the script compiling. That handler serves only regular files inside `out/renderer` and sends the window CSP from `src/main/csp.ts` with each one. On the first launch after the update, main copies every `file://` localStorage key the new origin lacks, such as the interface language and dismissed notices, and records the copy in `userData/storage-carried.json` so it runs once. The protocol handlers resolve the current workspace on every request, including after a move. A workspace move stops core, verifies a staged copy, commits the path, then starts the replacement core before removing the original. Automatic backups run in a worker thread while core keeps running; a manual backup, restore, move or wipe stops a running one first. See [automatic backups](data-model.md#automatic-backups).

The application menu is built in `src/main/menu.ts` for every platform and build; development builds add reload and developer tools. Menu text lives in main, in Italian and English. The renderer reports its interface language through `setMenuLanguage`, and main rebuilds the menu when it changes. A menu pick sends one command from the list in `src/shared/menu.ts` to the renderer, and the preload drops anything not on that list. `MenuCommands` in the renderer runs the command through the router, but only if `menu-guard.ts` allows it: not during onboarding, with a dialog open, while a page holds a lock (`useMenuLock` in `menu-state.ts`, used by the timed simulation, the plan wizard and setup), or while focus is in a text field whose text would be lost. The Ask composer is exempt because it keeps a draft per chat, and so is Indietro on a page whose way back saves first (a `beforeLeave` in `usePlace`, as the quiz and a flashcard session have), though never Avanti. On a page with a leave guard (`useLeaveGuard`, held by setup again and the exercises page while an answer is typed, besides the pages that had one) every command that moves through the router is exempt, Avanti included, because the guard asks "Uscire senza salvare?" before the move; reporting a problem opens the browser, which the guard cannot hold, and stays refused. `keepsTyped` in the menu context carries both cases. The quiz holds the lock only while its newest answers are not saved (`unsaved` in `draftSaver.ts`). A Vai section goes straight to its main page and starts a new trail, through the same `sectionNavigation` (`app/sections.ts`) as the sidebar's rows. Indietro runs the back control the page on screen registered through `usePlace` (`app/back-slot.ts`), the same `go()` as the button, and Avanti goes one entry forward. The mouse's side buttons (3 and 4, read as `mouseup` in `MenuCommands`) and the three-finger swipe on macOS (Electron's legacy `swipe` event on the window in main, which Electron's documentation says macOS sends only when the trackpad's "Swipe between pages" is set to "Swipe with two or three fingers"; it documents no event for the two-finger gesture) send the same two commands. The renderer reports through `setNavState` which of the two can do something now: Indietro needs a registered back control, Avanti needs an entry ahead in the trail (`canForward`), and neither is on while a page holds a lock. Main validates the two booleans, greys the items in the menu that stands and keeps the state across a rebuild. Help > Keyboard shortcuts opens a dialog that is the one list of every shortcut; add a key to a page and to that list together. A new page for the Go menu is one entry in `goPages` plus its labels.

Electron gives a page no right-click menu, so main builds the one for text (`textMenuTemplate` in `src/main/menu.ts`) from the window's `context-menu` event, in the interface language: Annulla, Ripeti, Taglia, Copia, Incolla and Seleziona tutto in an editable field, each on only when the field allows it, spelling suggestions with "Aggiungi al dizionario", and Copia on selected text elsewhere. Its items are roles and the two spelling actions in main, so the page sends nothing. The window's own item menus prevent the page's `contextmenu`, and Chromium then sends main no event, so the two menus never both open. Spellcheck is on, as Electron's default, in the computer's language. `src/main/spellcheck.ts` can point it at the app's language and the other one the app ships (`it-IT` and `en-US`, on Windows and Linux; macOS's own checker chooses), at start and when the interface language changes, but `SPELLCHECK_FOLLOWS_APP_LANGUAGE` is off: Chromium downloads each dictionary from `redirector.gvt1.com` on first use (one file per language, once per profile), and that request is not in SECURITY.md until the owner allows it.

A `.pyxis` plan file that the system opens with Pyxis, or a second launch passes, is queued in main (`open-file` on macOS, the file argument and `second-instance` elsewhere). Main checks its name, type and size and reads it only when the renderer calls `openedPlan.take`; the renderer never passes a path. `OpenedPlans` in the renderer also takes a file dropped on the window, and sends both to the shared-plan page under the same guard as menu commands. See `src/main/plan-open.ts` and "Opening and importing" in `plan-file.md`.

The renderer keeps a trail beside the window's history (`app/trail.ts`, connected in `app/history.ts`): one record per history entry, keyed by the router location's key and the entry's `idx`, with the entry it was opened from, the name its page gave itself and what had the focus when the student left it. The router reports every navigation it finishes. A push records the page that was showing as its origin, a replace keeps the replaced entry's origin, so a redirect or an address a page rewrites does not break it, and a pop changes nothing. A sidebar row, a Vai section and a page opened from outside (a reminder, a `.pyxis` file) pass `state: { via }` and start without an origin. Each entry also records the `section` it lights in the sidebar: the section of its own path when it starts a trail or is a chat, otherwise the section of the page that opened it, so a map opened from an exam keeps Esami lit and Settings opened over it does too (`useSection` reads it for the page showing or opening). The trail lives in session storage, capped at 200 entries, so a reload keeps it and a new window starts without one; a trail that does not parse means no history. Each page calls `usePlace` (`app/usePlace.ts`), which names the page on its entry and returns its way back: a move back in history to the origin, or, with no origin or a deleted one (`forgetPlaces`), its parent from `app/places.ts` in place of the entry. `places.test.ts` fails when a route in `router.tsx` has no row there. After a move back, the focus returns to the element that opened the page left behind, found by its `data-focus-key`, id, link or name.

Core owns `pyxis.db`, blob storage and domain handlers. `src/shared/ipc.ts` defines request, response and event shapes. Core parses inputs with Zod before dispatching. Errors use `{ code, messageKey, params, detail }`. `src/shared/bridge.ts` describes privileged main/preload operations separately.

Main transfers a fresh message port between core and renderer. React Query handles renderer request state and invalidation. The exam list, plan and Progress queries stay fresh for 30 s; a finished job or the `plans.evidence` broadcast marks them stale sooner. A job update refreshes only what its kind changes: the sources for an import, the build progress for a plan build, the download state for a download. Plans refresh when a job ends. Updates less than 250 ms apart refresh together. Streams have cancellation; job updates arrive as events. If core exits, main restarts it and transfers a new port. In-flight requests reject with `core-restarted` so the renderer can show the failure and reconnect.

## Storage and jobs

SQLite uses WAL with `synchronous = NORMAL`, foreign keys and numbered transactional migrations. Main stops core by message, and core checkpoints the WAL and closes the database before it exits. Passages have an FTS index and optional local embeddings in sqlite-vec. Source bytes live in content-addressed blobs. Extraction creates immutable document versions; citations retain passage IDs and locator metadata. See [data model](data-model.md).

`src/core/jobs/runner.ts` stores jobs and named steps in SQLite. A successful step stores its output before the next step. Retry preserves completed steps; cancellation aborts the active work. Startup changes unfinished running work to interrupted so it can resume. Imports, indexing and the OCR and search-model downloads resume on their own when their next step is local work (`resumeLocal`), once per step, so a step that keeps ending the process waits for the student. A step that calls a model, such as a photo's vision read, waits for Resume. An import resumed in its index step leaves its source ready while the vectors are redone. A step an update retired stays registered with `retired: true`, so a job saved before the update can still finish it. New jobs leave it out. Source imports, plan creation, generation and simulation grading register feature-specific step handlers. Some short operations are direct IPC requests.

"Ferma tutte" in Attività calls `jobs.stopAll`, which cancels every queued and running job except the work a page does itself, with no confirmation. The stopped jobs wait under "C'è bisogno di te" as one item, and its Riprendi calls `jobs.resumeAll`, which queues them again from the step each had reached, in the order they were made. A kind can name the request a job came from (`group` in its `JobSpec`, `JobView.group`): an import names its linked folder (`folderId`) or the Library batch it came with, and the index checks a plan change queues share one batch. The list shows the jobs of one kind and one request as one row from two jobs up, and `JobView.group.waiting` counts the folder's files not queued yet, so the row reads "Leggo le fonti · 12 di 37". A job that stopped because its AI tool ran out of requests has its own row under "C'è bisogno di te", with the choices to go on with the next tool, to wait until the requests are back and to open the tools in Settings; see [a job whose tool ran out of requests](engines.md#a-job-whose-tool-ran-out-of-requests).

Image imports use the selected vision engine when its model supports images, with the same provider acknowledgement as other generation (confirmed at setup, in Settings or once at launch; a task never waits for it, and automatic selection skips an engine that is not acknowledged). Otherwise they use local OCR, which reads English and Italian `tessdata_fast` files pinned to one tesseract-ocr commit (`src/core/sources/ocr-data.ts`). Pyxis downloads them by itself once setup is done, as the `ocr-data-download` job in Attività (one step per language, so it shows progress, and it can be cancelled and retried): the shell asks core for it at each start (`sources.ocrDataAuto`), which does nothing when the files are ready and replaces a download that stopped. A screen that needs the data starts it the same way if nothing is downloading it. End-to-end runs download only from the local server that `PYXIS_E2E_OCR_BASE` names. Every OCR run reads them back, checks size and SHA-256, and gives tesseract.js a private local folder of exactly those bytes, so the library's CDN default and its cache are never used. Without the data, a photo import, a chat photo, a scanned-PDF page and a HEIC fail by name (`ocr-data-missing`, or `ocr-data-integrity` for an altered file) before any row or page is queued. The requests are `sources.ocrDataState`, `sources.ocrDataAuto` and `sources.ocrData`.

A scanned PDF (no text layer) is read by the `source-ocr` job in core (`src/core/sources/ocr-job.ts`). An extract worker draws 8 pages at a time with pdf.js and `@napi-rs/canvas`, then reads them with Tesseract. A Word file whose text is shorter than 30 characters per picture, and a presentation whose slides are mostly pictures with almost no text, are scans too: the same job reads their PNG and JPEG pictures in reading order, 8 at a time, each stored as a passage named `picture N` or `slide N`, whose locator holds its number among the pictures and, in a deck, its slide (`scanPictures()` in `src/core/sources/documents.ts`). Their own text is kept, however short, and the scan ends ready when the file has any passage. A picture that cannot be decoded reads as blank. Core stores each page as it comes back and moves the job's progress. Core's main thread keeps the canvas addon loaded, so a worker that stops cannot leave the addon's thread behind on Windows. The window only watches the job, so leaving the Library, reloading or closing the window does not stop it. A quit leaves the job interrupted with its pages kept, and the next start resumes it from the first page without text. A run that dies again before storing a page waits for the student's Resume instead. The job starts by itself after an import that turns out to be a scan, and when the OCR data download finishes, unless the student turned the download off. Otherwise the Library and the exam wizard offer "Read the scan" (`sources.ocr`). Stop, a failure, or a replaced file puts the scan back to `needs-ocr`, keeping the pages read.

Failed vision extraction falls back to OCR, while cancellation or declined disclosure stops the job. Original HEIC/HEIF bytes stay in the blob store; decoded PNG pixels go to vision or OCR in a worker. The document records its extraction path, actual model and versioned prompt. Native file drops resolve real `File` objects in preload and receive the same bounded file grants as picker imports.

Material comes into the Library once. `enqueueSourceData` looks the content up before it stores anything: the SHA-256 of the bytes for a file or pasted text, the web address for a link. A usable Library source that already holds it (not removed, failed, cancelled or interrupted) is returned and no job starts, whichever way the material came in. The lookup covers a file a linked folder reads in place, through the `content_hash` on its `linked_files` row while the file is present (an index on that column keeps the lookup short when a scan asks for thousands of files). A copy that a chat or a plan file keeps out of the Library (`library = 0`) does not count, because it goes with that chat or plan: importing the same file makes the Library its own source, and deleting the chat leaves that source alone. Nothing awaits between the lookup and the insert, so a file chosen twice in one request, or again while its first import is still queued or being read, ends as one source. Core throws `SourceExists` and the `sources.import`, `sources.paste` and `sources.link` handlers answer with that source and `existing: true`; the Library says "Già in libreria: uso quella." and selects it. Replacing a source's file (`existingId`) is not checked, since the student asked for that source to change.

A file, pasted text or link added from the Library page gets a subject chosen by Pyxis (`src/core/sources/library-subjects.ts`). The page passes `sort: true` with each import, which marks a new source `subject_sort = 'waiting'`, and then asks `sources.sortSubjects` once for the whole add, which starts one `library-sort` job, one row in Attività. Exam pages, chat attachments and plan files never ask, and linked folders keep their own sorting. The job first waits, holding no slot and for at most 90 seconds, until the files' first reading is over, so the AI tool sees what each is about; reading never waits for it. Then it calls `sortLibraryFiles` (`linked-subjects.ts`, prompt `library.sort`, the `default` feature), which shares its engine, time limit and error handling with the sorter of loose files in linked folders: 100 files a call with the subject names the student has, and each file with an `id` (its place in the call), its name and the first 400 characters of its text once read. The answer goes by `id`, so files with one title never share an answer, and a file the answer omits or names with an `id` that was not sent waits for the student. The job takes the subjects' ids before the call and resolves an answer through them, so a subject renamed meanwhile still receives its file, and one deleted meanwhile is not made again (the file waits for the student). The answer puts a file in one of those subjects, proposes a new subject (made once and shared by every file of the job given the same name, reusing a subject with that name in any case, also one the student made meanwhile), or leaves it to the student. A file Pyxis made a subject for is `created`, and its row says "Materia nuova" with Rinomina until that subject is renamed. A file left to the student is `unsure`, or `no-ai` without an AI tool, and waits in "Da sistemare" with a subject picker. Each file is written only while it is still `waiting`, so a choice the student made meanwhile stands, and a file the student placed (`manual`, from "Sposta in" or "Da sistemare") is never sorted again. A failed call fails the job with its files still waiting, which Riprova asks again; a stopped job leaves them in "Da sistemare" until Riprendi. A file read from a linked folder moves the same way, in Pyxis only: the file on disk stays where it is, the move marks its row as asked about (`sorted_at`), so the sort of loose files leaves it alone, and `manual` keeps setup again and a move on disk from changing it (see [linked folders](#linked-folders)).

A PowerPoint import adds each slide's speaker notes, found through the slide's relationships, to that slide's passage after the label `Speaker notes:`. A PDF locked with a password stops as `pdf-password-required` (or `pdf-password-wrong`). The student's answer goes to core with `sources.unlockPdf`, which keeps it in memory for the one read of that import and never in the job's input, so a retry or a resume after a restart asks again. A source saved from a link can be fetched again with `sources.refresh`: a changed page becomes the next extraction version of the same source, as a re-extract or a book update does, and older passages keep the copy they were read from.

Long extraction and embedding work runs in workers, so IPC stays responsive. The embedding model loads once in one embedding worker, which serves calls in order and releases the model after a minute without work. A search goes before waiting indexing batches. The worker thread stays up for the life of core, and a cancel stops inside it, because ONNX Runtime can abort the process when its thread is terminated or replaced (#58).

### Linked folders

A linked folder is one of the student's own folders that Pyxis reads in place (`src/core/sources/linked.ts`). Pyxis keeps the extracted text and the page index of each file, never a copy of it, and only reads: nothing creates, renames, moves or deletes anything inside the folder, and no temporary or sidecar file goes there. Setup links folders in one of two modes. In `root` mode the folder holds the student's whole study and each first-level subfolder is a subject; files at its top level stay without a subject, unless it has no subfolders with material, when the folder itself is the subject. In `subject` mode each folder picked is one subject, whatever its subfolders.

`sources.linkFolders` takes the paths main's folder picker or a drop granted. A folder dropped on setup's folder step reaches main through `grantDroppedFolders`, which, as for dropped files, reads the path from the real `File` in preload and grants only a directory. Core checks each against the folder grants at the IPC boundary, as a folder import is checked, and the handler then refuses a path that is not an absolute directory (`folder-missing`), one inside the workspace or the app's data (`folder-inside-data`), and one inside a linked folder or holding one (`folder-overlap`). A walk never enters the workspace or the app's data, so linking the home folder does not read Pyxis's own files.

A linked folder is read in full, with no cap on files. Hidden names and symlinks are skipped, so a link can never lead the walk into a cycle, and folders nested more than 32 levels deep are not opened (`MAX_LINKED_DEPTH`); the look records that cut, and one for a subfolder the system would not open, in `cut_json`, and setup says so. The walk (`walkImportable` in `folder.ts`) reads each folder through the thread pool a few entries at a time and lets the event loop go every 256 entries, so core keeps answering requests while it reads tens of thousands of files.

Linking does not wait for the full walk. It reads each first-level subfolder only up to 40 file names or 5,000 entries (`peekFolder`), enough to name its subjects, and returns at once; the full walk runs in the background. Subjects are named with one model call per 60 folders for all the folders a request links (`linked-subjects.ts`, prompt `folders.subjects`, the `default` feature). It sends the folder names and, for each, up to 40 file names relative to it, never a file's content. The answer, validated against a schema, tidies each name ("Fisica 1" becomes "Fisica I"), marks a folder that is not study material (in `root` mode only) and names the kinds of material: book, slides, exams, notes, exercises and handouts. Without a ready engine, or when the calls fail or take more than 60 seconds, the folder names are used as they are and nothing is skipped. Reading starts as soon as the folders are linked, for every subfolder that is not skipped. A subfolder whose material lay past the sample is found by the walk and named as the folder is.

Files lying loose at the top of a `root` folder that has subject subfolders are sorted into those subjects by name (prompt `folders.sort`), 100 names a call, after the walk records them. The model sees the subjects and the file names, never a file's content, and answers with the subfolder each file belongs to, or none. A sorted file takes that subfolder in `linked_files.subfolder`, so it follows that subject from then on, and `sorted_at` keeps it from being asked about again. Without an AI tool the loose files stay without a subject and a later look asks again; after a failed call a `linked-folder-sort` job asks once more, and when that fails too it ends as a failed job in Attività (`linked-sort-failed`) with the files still without a subject; the folder is not asked again until the next start, or until Riprova on that job. `sources.confirmFolders` then saves the names the student confirmed: each creates a subject or reuses the one with that name, and the subfolder's sources take it. A skipped subfolder marked as a subject is read then. A folder setup never confirmed gets the names it offered at the next start.

A look records each new file as a `linked_files` row with `pending = 1` and no source, in one transaction per batch of 256. A queue (`pump` in `linked.ts`) then hands recorded files to the job queue oldest first, only while fewer than 48 `source-import` jobs wait or run, every 400 ms. A folder of tens of thousands of files therefore never fills the job queue or the jobs list, and a restart carries on with the files still recorded as waiting: the queued imports resume, and the look at start finds every recorded file unchanged. A changed file waits the same way, as `pending = 2`. The queue leaves a folder's new files alone while its walk is running, because one of them may turn out to be a file that moved. It also leaves a folder alone while the student has some of its readings stopped, until they are resumed or cleared, so stopping them does not just hand over the next files. Each file becomes a source with no stored original (`blob_sha` is NULL) when the queue takes it, under its subfolder's subject at that moment. Its `source-import` job carries `linked: true` and reads the file from its real path in the extract worker, after checking that it is still a regular file inside the folder, and hashes it there for the row. A scanned PDF is read by the `source-ocr` job from the same path. Photos are read by local OCR only, never by a vision model, so a folder of photos does not spend the student's AI requests; until the OCR data is downloaded they are left unrecorded, and the download's end looks at every folder again.

Core looks at every linked folder again at each start and whenever the folder's watch sees a change: a recursive `fs.watch` that runs the look 2 seconds after the last event of a burst, or 20 seconds after the first while events keep coming, and that closes when core shuts down. A look after a watch reads only the places the burst named (a subfolder, or one file and the rows under its path), so a change in a folder of 50,000 files does not walk the other 49,999. A burst with an unnamed event, or more than 256 places, reads the whole folder. A look that lasts longer than a second shows in Attività as "Leggo la cartella: N file trovati" (`linked-folder-read`, through `Runner.track` with `keep: false`, so it leaves no finished job). A look compares each file's size and modification time with its row:

| What the look finds                                  | What happens                                                                                                                      |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| A new file                                           | A new source with its import job, under its subfolder's subject                                                                   |
| A file whose size or time changed                    | Hashed first. Same contents: only the row changes. Otherwise the next version is read                                             |
| A new file with the size and hash of one that's gone | A move: the row and its source follow the file, into another subject if it moved, unless the student chose its subject (`manual`) |
| A file no longer there                               | `missing_at` is set. The source, its text and its citations stay                                                                  |
| A missing file that's back                           | `missing_at` is cleared                                                                                                           |
| The whole folder gone                                | Every file is missing until the folder is back                                                                                    |

The Library shows the subjects the student has, and the student can change them there. A subject renamed in the Library keeps its id, which `linked_subfolders.subject_id` holds, so a later look files new files under the new name and never makes a subject with the old one. Only a subject that nothing has (no Library file, exam, map, flashcard or chat) can be deleted from the Library (`subjects.remove` with `onlyEmpty`). Deleting it clears the subject of the subfolders that named it, which stay linked without one: a later look does not make the subject again, and new files in that subfolder wait in "Da sistemare". Setup again can give the subfolder a subject once more.

A look that marks a file missing, finds one again or follows a move sends the `sources.changed` broadcast, so the Library reads its list again; new and changed files are announced by their jobs. A walk that the depth cap cut, or that met an unreadable subfolder, marks nothing missing, because it cannot tell a file that is gone from one it did not reach. A changed file whose source has an unfinished job waits for the next look. A new version is published as a re-read is: older passages stay and the items that cite them are marked stale. A source the student removed from the Library is not read again, and a deleted one leaves its row with a NULL `source_id` for the same reason. A new file with the same bytes as a file imported into the Library earlier takes over that copy instead of making a second source. A look hashes the new files whose size matches a stored original, as it does for moves, and points the file's row at the copy, so the Library shows it once with its text, versions and citations as they were, and nothing is read again. The copy takes the subfolder's subject when it has none and keeps its own otherwise, also when setup is confirmed later. A subject it took from the folder follows the folder: when confirming gives the subfolder another subject, a copy with no subject or with the subfolder's previous one moves to the new one, and a copy with a subject of its own stays. It keeps its stored original, which it is read from while the file is unchanged (a scan's OCR included) and which keeps it in the subject's maps while the file is missing. Once the file changes, the next version is read from the folder and the source stops naming the original as its current file; the first version still names it, so the original stays stored. A copy kept out of the Library by a chat or a plan file, a link's page, a failed or removed import, a copy another linked file already took over and a copy being replaced with another file (its stored original is not the text it is about to hold) are not taken over, and files recorded before this look (such as at a restart) are read as their own sources. The Library shows a linked source's subject, and "Moved or deleted" for a missing file. The tables are in [data model](data-model.md).

The Library's head has one control for the linked folders, "3 cartelle collegate", which opens a list of them (`LinkedFolders.tsx`). Each folder shows how many files Pyxis reads there and how many of them are read (a file counts as read only when its reading ended with a usable source; `failed` counts the ones whose reading failed, was stopped or waits for the student, and the row says so and sends the student to Attività, where Riprova is, while the shelf marks those files), when the last look ended (`synced_at`), and whether a look or a reading is running or the folder is no longer on disk (`state` in `sources.linkedFolders`). Its menu has three actions:

| Action            | Call                        | What happens                                                                                                                                                                                   |
| ----------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mostra nel Finder | `revealLinkedFolder` (main) | The window sends only the folder's id. Main asks core for that folder's path and opens it with `shell.openPath`, so a page can never have a path of its own choosing opened                    |
| Rileggi adesso    | `sources.rereadFolder`      | One full look at that folder, in the background, and its watch again if it had stopped. The list and Attività show it as any look                                                              |
| Scollega…         | `sources.unlinkFolder`      | After a confirmation, in one transaction: each of the folder's sources is removed as `sources.remove` removes one (`removeSource`), and the folder's row goes with its subfolder and file rows |

Unlinking removes what the folder brought and nothing else:

| What hung from the folder                         | After unlinking                                                                                                                                                                                                             |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Its files                                         | Marked `removed`: out of the Library, search, retrieval and every exam's material (`plan_sources`). Their passages stay                                                                                                     |
| A Library copy the folder took over               | Stays in the Library as an added file while its stored original is still its current file (`blob_sha` set and the blob present). A copy whose file changed in the folder reads the folder's text and leaves like the others |
| Its subjects                                      | Stay, even empty. The student deletes an empty one from the Library                                                                                                                                                         |
| Flashcards, maps, lessons and quizzes             | Stay, with the text they cite                                                                                                                                                                                               |
| Citations in answers and lessons                  | Stay. The source panel still shows the cited passage and says the source is no longer in the Library (state `removed` in `sources.panel`)                                                                                   |
| Its reading                                       | The look stops (it checks an abort signal between batches, so it writes nothing after), the watch closes, and every reading of its files is dropped from Attività (`Runner.discard`), so nothing offers to resume it        |
| Subfolder subjects, suggested kinds, file records | Deleted with the folder's row                                                                                                                                                                                               |
| The folder on disk                                | Untouched                                                                                                                                                                                                                   |

Linking the folder again reads it as new: its files become new sources, the removed ones stay removed for their citations, and a subject chosen by hand for one of its files before does not come back. A copy that stayed is taken over again, so nothing shows twice.

A folder that is no longer on disk shows "Trova la cartella…". The student picks where it went, through the folder picker's grant, and `sources.relocateFolder` takes it as the same folder when more than half of the files read from it are at the same relative path with the same size, counting only the files the folder's own walk would read there (regular files reached through real folders, never a link). Names and sizes are what Pyxis keeps of every file; a hash is kept only for some, and checking it would read every file. The folder then keeps its id, subjects and sources, and the look that follows finds its files again (a file copied with a new time is hashed and, with the same contents, only its row changes). Otherwise nothing changes, and the list says how many files matched and offers to link the picked folder as a new one.

### The source panel

The source panel shows a Library file at a page: from a cover, a row of an exam's material, or a citation in a chat, a lesson, a quiz's results, a map or a flashcard. `sources.panel` (`src/core/sources/panel.ts`) tells the window what it can draw: the file's type, whether its original can be read now (the copy Pyxis stores, or the linked file read in place), where its read is (`ready`, `reading`, `locked`, `failed`, `removed`), whether a linked file is missing, and the cited passage with its page. The window decides from that what to show (`components/sourcePanel.ts`): a PDF's page, an image, or the text Pyxis read laid out as a page for Word files, slides, plain text, saved web pages and free books.

A free PoliTost book can be read before it is in the Library. `sources.bookPreview` and `sources.bookChapter` take only the catalog id: core reads the catalog (the address and checksum are never the window's), downloads the package as an add would, checks its size and SHA-256, parses it with the import's own parser and keeps the result in one slot in memory (`book-reading.ts`), for ten minutes or until another book is read. Once the book is added and its read is over, the stored copy answers these requests and no package is needed. Nothing is written to the workspace or the database, so a reader closed without adding leaves nothing. `sources.importBook` takes the held bytes when they are the same package, so reading and then adding is one download, and takes an optional `subjectId` to put the book on that shelf. The panel draws this book like a stored one (`location.bookId`), without the selection menu, which needs stored passages. A book that is ticked as an exam's source, or with the first file of a new subject, is downloaded only when the exam is created or the file moved, by the same `sources.importBook`; a download that fails stops the exam, which keeps the form. The catalog is read only while the Library, the books list or an exam's material step is open, and a run with the test seams on (`PYXIS_E2E`) never reaches the real site: with no `PYXIS_E2E_BOOKS` folder it is offline.

A PDF is drawn by pdf.js in the window from bytes core reads on request (`sources.readOriginal`, at most 2 MiB a call). pdf.js asks for 64 KiB chunks and only for the ones the page it draws needs, so a 36 MB book of 900 pages opens at page 412 having read about 280 KB of it. A longer range, such as a large picture's stream, is read in pieces of at most 2 MiB. A read that fails ends the load: a file core reports as `source-file-missing` shows the panel's missing state (a linked file that moved, or a stored copy that is gone, each with its own words), and any other failure shows Riprova. The window keeps one picture of the page on screen and of the two seen before it, at the width drawn last, and lets go of the others. The request names the source or the passage by id, and core reads only that source's stored copy or its linked file, after checking that the linked file is still a regular file inside its folder. A citation keeps the version it was read from: an older version's own stored copy is read when it has one, with that version's kind (from its tree) and type (from the copy's own record), since a replacement can change both.

"Apri il file" asks main to open a source by its id (`openSourceFile`). Main asks core which file that is, and core answers only for a source still in the Library. A linked file opens in place. A stored copy is named by its hash with no extension, and the system picks the app by the extension, so main copies it to `userData/open-copies/<source id>/<hash>/<file name>` first and the system's app opens the copy (`src/main/open-copies.ts`). The folders are the record of the copies, so a run that crashed leaves nothing main can't find. A copy goes when core no longer has that file in the Library: core tells main after a removal, an unlinked folder, a deleted chat, a finished job or a look that changed something (`library-changed`), and main asks core about each copy. All of them go before a wipe or a restore replaces the workspace, when the app quits and at the next start. A copy an app still holds open, which Windows refuses to delete, stays until one of the next tries. The window never names a path.

### Import limits

Core checks a file's size before it allocates a buffer for it. An import job reads its file in the extract worker, two at a time across all jobs; the next step stores the passages under the hash the file was queued with, without reading the file into core again.

| Input                     | Limit                                                          |
| ------------------------- | -------------------------------------------------------------- |
| Document import           | 256 MB                                                         |
| Photo import              | 40 MB                                                          |
| Chat attachment           | The Library's: 256 MB a document, 40 MB a photo, no time limit |
| One ZIP entry             | 64 MiB inflated                                                |
| `.docx` or `.pptx`, total | 128 MiB inflated                                               |
| Smartbook, total          | 256 MiB inflated                                               |
| Folder import (a copy)    | 2,000 files, 12 levels deep, 20,000 entries read               |
| Linked folder             | No file cap, 32 levels deep                                    |
| Extract worker heap       | 2 GiB of V8 heap                                               |

The IPC server reads the size from `fstat` and refuses a file that grows past its cap during the read.

### Files attached to a chat

A file is read when it is attached, not when the question is sent (`src/core/chat/held-files.ts`). `chats.attach` takes a path the picker or a drop granted, behind the same file boundary and size caps as a Library import, and answers at once with the file's chip (`AttachmentView`: name, kind, size, state, how far the reading is and why it failed). The reading goes on in core and every change arrives as `chats.attachment`. A document is queued as the Library queues one (`enqueueSourceFile` with `hidden`, a source with `library = 0`), so it uses the same extract worker, the same limits and the same `source-import` job; a scan that comes out of it starts the Library's `source-ocr` job, page by page, when the student agreed to local OCR and its data is on this computer, and the chip says "page N of M" (`pages` is kept in the scan job's parameters). Without the data the chip is `needs-data` and the page shows the OCR download card, and `chats.attachScan` starts the scan once it is here. Both jobs are marked `held` in their parameters and are `unlisted` (`JobSpec.unlisted`), so Attività never shows them, and the mark stays when the file is taken off and its source is gone. A photo is stored and fitted for a model in the extract worker; its chip is ready when that ends.

Removing a chip (`chats.detach`) cancels its jobs and gives them up (`Runner.discard`), deletes the hidden source with its passages and the stored photo unless something else uses them. Every held file is also a row of `held_files` from the moment it is attached: its draft (a chat id, or empty for a new chat), the hidden source or the stored photo, the extracted-text file of its import and its state. Core keeps the running parts (the reading, the fitted copy) in memory until the question that carries the file is stored and answered, so leaving the chat and coming back, reloading the window or a failed turn keeps the chips ready (`chats.attachments` asks which ids core still holds). One query answers whether a source or a stored file is still wanted, and every cleanup uses it: `sourceInUse` and `BLOB_REFERENCES` count `held_files` and `attachments.source_id` as well as a chat's scope, plans and citations. That covers a deleted chat or plan, Free up space, taking a file off (which also removes the import's extracted-text file) and the sweep at start (`sweep`), which removes every row the last run left, through the same path as taking a file off, so what a stored question names stays. Removing a stored file (`removeBlob`) renames it to a temporary name before deleting it, so the blob's own name is free at once: on Windows a file that something still holds open is only marked for deletion, and until the holder lets go its name cannot be opened or replaced, which made a file attached again right after it was taken off fail to read. A file the system will not rename stays whole under its name, and only a file is renamed: a directory or a link where a blob should be is left in place. When the system will not delete the renamed file either, it stays under its temporary name until core starts again, which removes those names (and a write's leftovers) with the code Free up space uses (`removeBlobLeftovers`), or until Free up space runs. A file is tied to the question that carries it once that is stored (`held_files.message_id`), and when the question is answered, by the turn or by a Try again, `finishSend` lets the tied files go: the ones its stored rows name are simply no longer held, and a copy the chat already had or a file that could not be read goes the way a file taken off does. Deleting a chat takes off the files its composer still held (`discardDraft`), and core refuses a pick for a chat that is gone. A new chat takes the files left in the draft it was made from (`rehome`, and the same move in the window, whether or not Chiedi is on screen). A held document the student cancelled ends as stopped, with no scan started, and a photo whose local OCR fails at send time is left out and named, so the question goes out. A draft removed while a file is being registered discards what the registration made. A photo the fitting says is unreadable fails on its chip; one only past the provider's size limit is ready and read by OCR. The JPEG decoder may use 1,536 MB (`JPEG_MEMORY_MB`), which reads a 48 MP photo of any kind (a 4:4:4 or progressive one needs about 900 MB), and a decode past it is refused under its own code (`vision-image-decode-limit`), never as damaged: the photo fails on its chip with its size reason when it is attached, since the local reading would decode it with the same limit, while a photo only past a provider's limit stays ready. The index job of a held scan carries the same `held` mark as its import and scan jobs. In the window, each draft has its own queue (`draftFiles.ts`): a batch of picked files runs after the earlier one, each result applies to the draft that asked for it, the ninth file of a draft is marked over the limit when it is picked, and a pick of a deleted chat is cancelled, a fresh pick replaces a refused chip, and a send starts its turn at once (the composer shows it working, with Stop) and waits for its draft's queue before it reads the files. Core announces every change of a file (`chats.attachment`), and a small photo is fitted before the answer to its attach has left core, so the window keeps the announcement it already holds and takes the answer only when it has none.

`chats.ask` takes the ids (`attachments`, at most eight, the one cap a message keeps because of the providers' own limits on images). The turn waits until none is still being read, goes on without the ones that failed and names them in `leftOut`. The question's own text is stored as typed. Each file goes in one row of `attachments` with its name, kind, size and, for a document, the hidden source's id (`chats.read` returns them as `files`); a photo's fitted copy carries the name, and its original is a plain row that a resend skips. The text local OCR reads from a photo goes in `attachments.recognised` and is sent with the question and with later turns, and never shown as message text. Chats saved before this keep the text in the body of the question.

A turn that has a photo, and every later turn of a chat that holds one, runs on a model that reads images when the chat's own does not and the choice is automatic, because the chat's [session](engines.md#chat-sessions-and-prompt-caching) holds the image and a model without image input may not resume it. Whether the picture itself is sent is decided for the tool that answers, as the prompt is: a photo read as text for a planned text-only tool also goes as a picture to an automatic choice that falls back to a tool that reads images (`attachmentsFor` in `generate()`), and a picture the planned tool reads never goes to a fallback that cannot read it. A turn that holds a photo on a local model has no fallback at all: the photo, the text read from it and the conversation would reach a cloud tool, so a failure of the local model ends the turn with its own error. A change of model on one tool continues the session: the model the same tool chooses for photos (`selectionOn(provider, "vision")`, kept as an automatic choice so a limit or a sign-out moves on to the next tool), then the one chosen for the vision task on another available tool, never from a local model to a cloud tool. A model the student pinned for the chat never moves: a photo it cannot read, or one with no usable copy for the model, goes to local OCR and its text is sent.

Office files and smartbooks open through `src/core/sources/zip-bounded.ts`. It reads the central directory only for locations, inflates just the entries it needs in small pushes, and counts the real output, so a lying header or overlapping entries cannot exceed the caps. mammoth only ever sees a stored archive that the reader rebuilt from the XML parts.

The heap limit does not cover buffers, WebAssembly or native decoders (pdf.js stream decoding, HEIC, OCR). Those stay bounded by the size caps and by cancellation. Folder scans hash files by streaming in the extract worker. The blur check and its hash run in the same worker.

### Photos sent to a vision model

A photo goes to a vision model as a fitted copy: at most 1.5 MB of raw bytes and 2,560 px on the long edge, turned upright from EXIF, with transparency flattened onto white, and re-encoded as JPEG when it had to shrink. That keeps eight new and four saved images inside the 5 MB per image and 32 MB per request limits Anthropic documents. The stored original is untouched.

A chat keeps the fitted copy and the original as two attachment rows. The original's type carries an `;original` suffix so a resend never sends both. An imported photo's document records the size sent and what it was resized from. WebP has no decoder here, so an oversized WebP goes through local OCR instead.

### Lessons, quizzes and concurrency

Long-topic lessons cover every passage in consecutive calls with at most 24,000 characters of source text per call. Citation numbers stay stable across parts. The lesson prompt asks for about six sections (five to seven) and at most six quick checks in the whole lesson; each part of a long topic gets its share of that, so a long topic does not grow into a long lesson. While a lesson is written, the lesson page shows each section once the next heading has appeared and a status naming the section in progress, so the text a student is reading never moves. The combined lesson is cached only after all parts pass validation, so a failed rewrite preserves the previous lesson. Prepared model-written simulations retain questions without starting an attempt; an explicit Start starts the clock. A plan with past exams (`src/core/study/pastPapers.ts`) reads each one with a `paper-read` job, and the simulation builder then copies their question count, types and difficulty; the simulation setup lets the student choose the standard format instead. Quiz deadlines are enforced in core against the saved answer draft. A timed quiz takes no answers or checks until every question is written, and its clock starts at the first save after that. A graded attempt, its evidence and its path step carry the time its answers froze, at submit or at time-up, not the time grading finished. An open answer in a quiz has a second, optional field for the steps that led to it. The steps travel beside the answers as `steps`, by question id, in the draft, the grading job and the saved result, and only those written under an answer are kept at hand-in. The grading prompt receives them with the answer, and the SymPy check reads them as the lines before it. Under the answer field, "Si legge" reads the answer's formulas back in Italian or English words (`answerReading` in `src/shared/math-words.ts`), and shows nothing for a formula it has no words for.

A topic's lesson can also be written in short parts (`src/core/study/parts.ts`, `partJobs.ts`). Each part is written by a queued `lesson-part` job, which is `interactive` because the part ahead is needed while the student reads the one before. The job has two steps: `outline` plans the topic's parts when it has no live outline and does nothing otherwise, so a retry after a failed write keeps the saved outline, and `write` writes the part at the job's position. Each part call gets the whole outline, the headings and summary of every part already written, and only that part's passages. Each passage belongs to one part, so no two calls teach from the same material, and the whole request stays within the same 24,000 characters as a lesson call: source headings are cut to 200 characters, every passage keeps some of its own text, and the request's size is checked before the call. `partShape` checks the reply before anything is saved: it repairs a fence around the reply, a leading title, extra question blocks and the closing `pyxis-takeaway`, which becomes the part's summary. It asks once more, with one line per broken rule, when the part has the wrong number of sections, does not end with its question, is too short or too long, repeats a heading of another part, or has no takeaway. A takeaway over 300 characters is cut, after its last whole sentence that fits when that keeps more than half of it, because a model counts characters badly and a rewrite of the whole part took 14 to 25 seconds. A second reply is saved when a page can show it, without its question if it has none, and otherwise the job fails with `lesson-part-invalid`. The part's lesson item, its summary and its measured minutes are saved in one transaction, so a cancel, an engine error, a missing engine or a quit leaves the outline and the earlier parts as they were. Every start goes through one function in one transaction: opening a part starts, resumes or retries that part's job, and opening a written part starts the part after it only when no part job of the topic is queued or running. A part whose last write failed or was cancelled is left for the student: the runner's `onFailed` and `onCancelled` hooks set the part's `write_failed_at` as its job reaches that state, so the mark outlives a job the student dismisses in Attività, and the part reads as failed until the student opens it again or a write succeeds. A quit is not a failure: the next start marks the job interrupted, and opening the part or the part before it resumes it. So a topic has at most one part written ahead of the one being read, plus the parts the student opened. `study.parts` lists a topic's parts, and `study.part` opens one, starts the part ahead, and reports `planning`, `writing`, `written`, `failed` or `book` (no engine set up: the part's passages as book text, not saved). A part is done when its last question is answered, or with "Fatto" when it has none, and the topic's lesson step is recorded when every part of its live outline is done, in whatever order they were read (`finishPart` in `partProgress.ts`); a part not written yet or whose write failed is not done, so it keeps the lesson unread. A lesson written before parts follows one rule in `src/core/study/oldLessons.ts`: it is finished when the topic's lesson step is recorded or its closing recap is answered in full. A finished one opens in the existing reader, and `study.rewriteInParts` ("Riscrivi in parti" in its menu) starts its rewrite. An unfinished one is rewritten in parts when the student opens it: the first open with `write` starts part 1's job, and the outline names the old lesson in `replaces_item_id`. The old lesson stays the topic's lesson until a part of the rewrite is written. One rule decides it, `outlineShown` and its SQL form `shownOutlineSql` in `parts.ts`: an outline made for a topic never read is the student's lesson at once, and one that replaces an old lesson only once one of its parts is written. `study.parts`, the suggestion's part (`nextPart`), the path's part progress (`outlineProgress`), and with it the minutes left and the rings, read that rule, so a rewrite that fails or finds no engine changes nothing on the exam page, while its stored outline waits for Riprova. Nothing ever deletes the old row, its answers or its citations, and while a replacement exists, or its job is running, the old lesson opened by its item is the earlier version, read-only, so nothing can rewrite it in one piece. The Markdown export of a topic in parts joins its written parts in order and lists the sources those parts were written from.

A written part can be written again. The level the student picks on a part (`study.part` with `wording`) is kept on the outline (`lesson_outlines.wording`) once a text at that level is saved, so every part written after it uses it, and the part after the one opened, written before at another level and not done, is written again at it under the same one-ahead rule. Each level of a part is its own lesson item, because the level is in the cache key: a level the part was written at before is shown again with no call, and the other texts keep their answers. `regenerate` writes the part again at its own level in the same item, so its earlier answers stay under the earlier questions' ids. Both run as the part's `lesson-part` job, with `rewrite` and `wording` in its parameters, and only change `item_id`, `summary` and, on a part not done, `minutes`: a part done stays done, and today's minutes do not move. `study.part` reports a rewrite that is writing or failed as `rewrite`, over the text the part has now. `study.lessonSection` with a `position` rewrites one section of a part in the part's own item, and the whole text must pass `partShape` again, so the part keeps its sections, its question at the end and a fresh summary. Every text of a part has the template `lesson.part` and its part's id as its cache key's scope, which is how a topic's finished items, the delete count, plan files and mastery tell a text at a level the part no longer shows from a lesson of its own.

The lesson page (`features/study/LessonPage.tsx`) reads `study.part` and shows `PartPage` for a lesson in parts, or the reader that came before parts (`LegacyLessonPage`) when core answers `legacy`. A part is `/plans/:planId/lesson/:topicId?part=3`, the same route, so moving between parts loads no new page; opened without `?part`, the page writes the part core chose into the address, and only while the lesson is still the page the router shows (`useStillHere`): a read that comes back after the student has left would otherwise take them back to the lesson. The page's first read of a part that nothing is writing sends `write`, so a part job starts or resumes; a part whose job failed waits for Riprova, so a failing call never repeats on its own. While a part is planned or written the page reads it every second, and every update of a `lesson-part` job makes it read at once (`staleFamilies`). The parts column, and its popover from the bar's title under 1,100 px, is `PartsList`; the end of a part is `PartFoot`. While an old lesson is rewritten the working block says so and opens the earlier version, read-only, through `?item=`; a rewrite that stops before any part is written shows the old lesson in its own reader under what happened, with Riprova, with its answers still open and without Livello or any rewrite of it. A finished lesson whose replacement is stored opens on that screen too.

Default limits are two CLI model jobs, four API model jobs, one demo job and `max(1, availableParallelism - 1)` local jobs. A job the student waits for on screen (checking a quiz answer, grading a quiz, writing a part, and writing a quiz the student just started, until its first questions are saved) is `interactive`: it counts only against other interactive jobs of its class, so it never queues behind a quiz being written or a mistake analysis, while background work still counts it. A step can give the place back with `ctx.background()`: the quiz build does when its first batch is saved, so a build and a part written ahead never hold both interactive places against a hand-in being graded. A topic quiz is written four questions per call, (on Antigravity at the lowest effort its model lists, by the model file's `lowEffort`), and saved after each call, so the quiz screen's count of ready questions moves while the student answers. A lesson being written, a lesson section rewrite and flashcards suggested from a selection are calls the page makes itself; core lists them in the jobs list with `Runner.track` while they run (without a cancel, since their page stops them) and keeps the ones that succeed as finished jobs. A plan build writes its introduction and its diagnostic in one step that holds one CLI slot and makes both calls at once. Each result is saved as it arrives, so a failed call keeps the other and a retry asks only for the missing one.

A page that waits on a job shows what the job's model call is doing. `runTurn()` follows each call of a job from the engine's events (`trackCall()` in `src/core/jobs/activity.ts`, one entry per call, so two calls of one job at once, such as two figure repairs of a part, do not remove each other's; the oldest one still running is shown): `starting` until the tool says something, `thinking` on its first reasoning event, `writing` on its first text. The state is in memory only and is cleared when the call ends. `study.part` gives it as `activity` while the part's job is queued or running (and in `rewrite` while a part is written again), and `study.quizRead` while the quiz is being written; the working block of the lesson, the waiting screen of the quiz and the answer sheet's count of ready questions show it as one line with the seconds since the call began ("Thinking it through · 0:42"), outside the live region so a screen reader does not read the seconds out. Debug mode's log for the job holds the same events with their times.

Python runs in a separate sandboxed renderer/worker context with local Pyodide, SymPy and MEMFS. A fresh worker isolates each run. The configured timeout interrupts execution and a hard timeout terminates it. It cannot read the Electron workspace through Node. Grading uses the same SymPy worker as the Ask checks (`check_grade` in `src/sandbox/symbolic.py`). For a math answer it compares the student's final answer with the reference (expressions, equations, solution sets and intervals) and finds the first step of a worked solution that does not follow from the one before. Core sends the verdict to the grading model as `mathCheck`, and credits a fill-in blank that is the same mathematics as an accepted answer. Grading waits at most 12 s for the check, and without the downloaded runtime, or when SymPy cannot read the text, it grades as before. Lessons and Ask answers can ask for a figure in a `pyxis-figure` block, whose `kind` says what its code is: matplotlib code for a `plot`, which is also what a block without a kind is, and schemdraw code for a `circuit`. `src/shared/figure-kinds.ts` is the one table of the kinds, with each kind's limits and the packs it needs. Core runs each figure's code in the sandbox once, with an 8-second limit and at most 4,000 characters, and stores the PNG with the lesson or message. Figure code comes from a model or from an imported plan file, so it runs nowhere else.

A figure that fails to draw gets one retry. `drawFigures` sends the block to the model once through `figureFixer`, with its kind, caption, code and the last 1,500 characters of the error (`resources/prompts/figure.fix.md`, reply `{code}`), and draws the corrected code. The call never sees the lesson or the answer around the block. It runs on the caller's own engine selection, run and stop signal, so the chat turn counts its tokens with the chat and a lesson job with the job, and a stopped job stops it. The block then carries the corrected code, which the image is stored for. A second failure, or a fix call that fails, removes the block and the rest of the text is saved as written. No call is made for a kind the workspace cannot draw, for a runtime that is missing or crashed, or for a fix that returns the code it was sent, and one text gets at most four, one per figure. `drawFigures` draws the figures of a text together, each as soon as it can be and none waiting for another, so a figure being corrected does not hold back the ones that are fine, and it tells each as it is settled (`onFigure`: its picture under the key of its block as written, or null for one left out). A chat answer sends those as `figure` events on the turn's stream, and its page shows each picture in its place while the others go on: a figure keeps its working state until its picture or its dropping comes, and the reply is saved, with the figures stored under the code each block carries, once all are settled. Stop pressed meanwhile keeps the answer's text and the figures already drawn, with the blocks of the ones still in progress left out, and the chat stays (`drawFigures` returns `stopped` instead of throwing). The legacy lesson page shows its figures the same way while it writes, but a lesson that is stopped is not saved, so a stop keeps none of them. A lesson part is written inside its job, whose own working state covers it, and a stopped part saves nothing.

An Ask answer's figures are also kept for the dark theme. `drawFigures` is called with `dark: true` by the chat turn only (lessons keep a single picture), and for each picture it draws it turns the PNG with `darkFigure` (`src/core/math/dark-figure.ts`): the white ground becomes the dark theme's `--surface`, black ink becomes its light ink, a light fill becomes a dark one and a colour in the middle keeps its hue and is lifted a little, pixel by pixel on the decoded 8-bit RGB or RGBA PNG. Nothing about the figure's code or its library matters, so there is no second render, and every kind (a plot, a circuit, a graph) is turned the same way. The result is stored under the figure's key with `-dark` (`darkFigureKey`), is told on the `figure` event as `dark`, and is left out when it cannot be made (another PNG kind) or is past `FIGURE_IMAGE_MAX`. A colour that is text or a stroke on white is lifted until it reads on the dark ground (4.7:1 for ink and dark colours, 3.5:1 for strokes in the middle), while light tints, fills and gridlines stay quiet. A figure stored before has no dark picture and stays on its white card in both themes, as do photos and scans, and the card shows the dark picture only in the dark theme. A continued reply keeps the dark picture its figures had. The student opens a figure in the picture viewer (`ImageViewer`, which grows from the figure's place with `grow()`), from its click or from the menu of its three dots, which a right-click and Shift+F10 open too; the menu offers Ingrandisci, Scarica PNG and Copia immagine, and download and copy work on the picture the theme shows.

The student downloads two packs: `pyodide` (Python, pinned in `resources/pyodide-manifest.json`) and `drawing` (the files that draw the other kinds of figure, today the schemdraw wheel and Graphviz, pinned in `resources/drawing-manifest.json` with a URL per file). Each pack has its own row in Settings › Studio › "Disegni e Python" (`PackRows.tsx`), with its own start, progress, failure, update and removal: `tools.runtimeDownload` takes the pack, starts one job for it (`local-runtime-download` for Python, `local-drawings-download` for the drawing pack) and joins a job that is already on its way, `tools.runtimeCancel` stops the download of one pack and no other, whoever started it (a row's Annulla, or the Python page's for every pack that is downloading), and `tools.runtimeRemove` takes a pack off the disk. The Python page keeps offering what is missing in one job for every missing pack. Main downloads each pack on its own (`downloadRuntime` in `src/main/runtime-pack.ts`), so a pack that fails or is cancelled leaves the other as it was, and `tools.runtime` reports each one: its phase, how far it got, its size, the version this app pins and whether the workspace holds an older one. Each pack has its folder, `workspace/runtimes/<pack>/<version>/`, and every file is checked against its size and SHA-256 after the download and again each time it is served. A folder of another version is never run, since this app's manifest cannot vouch for its files: the pack is offered as an update ("Aggiorna"), nothing is fetched until the student asks, and the drawings need the update before they draw again. Updating the drawing pack deletes the folders of its earlier versions once the new one is verified. Removing a pack stops its download, forgets its files before anything else can read them, deletes every version of it and closes the window that used it, so what it draws is unavailable at once and the prompts stop offering it; pictures already drawn stay, since they are stored with the text. Python runs need only `pyodide`, and a Python run installs the drawing pack's wheels before its code when that pack is there. A workspace that has Python but not the drawing pack keeps every Python feature. The prompts offer it plots only (`figureText` in `src/core/math/figures.ts` keeps the lines of the `figures` partial for the kinds that can be drawn). Nothing fetches a pack on its own: the only start is `runtimeDownload` in `src/core/math/handlers.ts`. The files come from the CDNs the manifests name (jsDelivr for Python and Graphviz, PyPI for the schemdraw wheel) and the request carries nothing of the student. An end-to-end run (`PYXIS_E2E=1` with `PYXIS_E2E_PACK_BASE`) gets them from a local server instead (`tests/e2e/pack-server.ts`). `node scripts/drawing-manifest.mjs` pins a changed file and records the licence texts of the pack's files.

Figures that are not Python are drawn in the drawing window (`src/main/draw-runtime.ts`), which today draws a `graph` (Graphviz DOT, `@hpcc-js/wasm-graphviz` from the drawing pack, which a graph needs alone, without Python). The text comes from a model or an imported plan file and the code from a download, so the window is built to be hostile-proof. It is hidden, sandboxed, isolated, without Node, without a preload and without WebGL. All its windows share one in-memory session (Electron never frees a session, so a session per window would leak one each time a window is replaced), whose storage is cleared each time a window goes. That session refuses every request that is not one of the window's own files (`runtime-protocol.ts` lists them per host, and a window's session answers for its own host only: the page, its script and its worker from the app, and the pack's JavaScript only after its hash is checked again, on every read for this pack), every permission and every download, and sends the network stack's own work, which the request filter does not see (WebRTC, `<link rel=preconnect>`, DNS), through a SOCKS proxy that is not there, loopback included, with WebRTC held to it. The Python sandbox's window is locked by the same helper (`runtime-window.ts`). The window refuses navigations, redirects and new windows. The page's CSP allows no network, no eval, no inline script, no frame, pictures from `blob:` and `data:` only and one worker, the file that runs Graphviz.

Graphviz runs in that worker (`draw-worker.ts`), which has no DOM and shares nothing with the page, so the pack's code cannot patch the page's sanitiser or its canvas code. The worker first has Graphviz parse the text and refuses it by what Graphviz understood (`inspect-dot.ts`): its own counts of nodes and edges are held to 150 and 300, and the text Graphviz writes back out is read for the attributes that name a file, a link or an element, the layout and the font names, so a spelling the text checks did not foresee still reaches no layout. A DOT text is also checked before that, in core and again in main (`src/shared/dot.ts`, read as Graphviz's lexer reads it: strings joined by `+` or by a backslash and a newline, a subgraph named again standing for what it holds, HTML-like labels refused). The page cleans the SVG with DOMPurify, bundled into the page's own script and never from the pack, keeps only the elements a drawing is made of, sets its text in Figtree (embedded in the picture from the app's own font file, so nothing is loaded), draws it on a white ground as a PNG at the density of the plots (longest side 2,000 pixels) and hands it back. Main accepts only a PNG data URL of at most `FIGURE_IMAGE_MAX` characters, with a PNG header and a size in pixels it expects, or a failure with a short plain message, cut before it is read. One drawing runs at a time. A drawing over its kind's time limit (5 seconds for a graph) or over 512 MB of working set, read every 250 ms, destroys the window and fails the request. A window whose renderer crashed, or that could not load its library, is replaced, and a pack file that failed its hash makes the pack not ready until it is downloaded again.

One gap is known. A `<link rel=dns-prefetch>` that code in the page makes is resolved by Chromium itself, as a speculative lookup through the machine's own resolver, whatever the proxy is, and the page's CSP does not govern it. Only code in the page can make one: the page never does, and the pack's code runs in a worker, which has no DOM. A message the page sends to main is copied across `executeJavaScript` before main can cut it, which cannot be bounded without a preload, so its size is bounded by the window's memory limit.

### Formulas

Formulas are drawn by KaTeX with mhchem, through `react-markdown`, `remark-math` and `rehype-katex` (`src/renderer/src/markdown/plugins.ts`). Every Markdown view first passes its text through `markdownSource` (`markdown/source.ts`), which links citations and calls `normalizeMathDelimiters` and `displayMathLines` (`src/shared/math-delimiters.ts`) to repair what a model's formulas need before remark-math reads them.

Those repairs do not scan Markdown by hand. `src/shared/markdown-tree.ts` parses the text with the renderer's own parser (`remark-parse`, `remark-gfm`, `remark-math`), and every repair is decided from that tree and applied to the source ranges it calls prose, never to code. `mapOutsideCode` (`src/shared/outside-code.ts`) uses the same tree for fenced and indented code blocks and code spans, so a fence in a longer fence, a backtick in a formula, a fence after a line with a dollar sign and an indented example are what the parser says they are. The repairs, in order:

- A `$$` block that remark-math misreads, which has content on its opening line or a closing `$$` after its last line, gets its delimiters on lines of their own, behind the quote marks or list indentation of the container it is in. Otherwise remark-math reads the first line as an info string and pairs every `$` after the block with the wrong one.
- `\( … \)` and `\[ … \]` become `$ … $` and `$$ … $$`. An inline pair is in one paragraph, heading or table cell of the parse, a display pair does not leave its quote or list item, and a pair with a code span or a formula inside is left alone.
- A `\$` that remark-math took for the end of a formula becomes `\char36{}`, because it ends the formula at its `$`. Which ones sit in formulas is read from a parse of the text with every `\$` already written that way, and one in a formula the parser read and KaTeX draws is left alone.
- A price that remark-math paired with the next dollar sign (`$25 and the area is $`, `25 $ e l'area è $`, or `$5.` and a `$$` fence on the next line) is escaped, and so is a dollar sign left as text in a block with a converted formula.
- A line or a standalone fence that holds only `\ce{…}` or `\pu{…}` is a display formula, and a paragraph that is only LaTeX with something mathematical in it, such as the answer of a worked example, is an inline one.

A formula KaTeX cannot draw shows as its source, in the text's own colour and a monospace face (`px-formula-source`), never in KaTeX's red. `rehypeQuietFormulas` asks KaTeX before `rehype-katex` runs (it throws where it cannot draw, and nothing about its output says so, a colour included), and `formulaHtml` does the same for the views that call KaTeX themselves (the message the student wrote, the graph page). The failures are counted in the window; the crash-report channel hears about them with the fixed code `formula-not-drawn`, at most once every ten minutes, which carries no text and sends nothing while its switch is off.

While an answer is being written, `MarkdownView` gets `drawing`, and `holdOpenMath` turns a formula whose closing delimiter has not arrived into a placeholder bar of about its size (`px-formula-pending`, a link written as `pyxis-math:<inline|display>:<characters so far>`), so half a formula never shows as source or as a KaTeX error. The parser says what is open: the last block is an unfinished `$$` block, or it ends in a `\(`, a `\[`, a `$$` or a `$` that the parser left as text with a formula after it (a letter, a command or something mathematical). A `$` and a number and then words is a price and stays text, and a `$` with nothing after it yet may be either. A formula that starts with a digit shows as text until its first command or operator arrives, for that reason. The chat and the lessons written before parts stream; a lesson part appears once it is written.

`src/renderer/src/markdown/formula-corpus.json` holds the answers of the four AI tools recorded on 2026-11-19 (the texts that broke and the most formula-heavy text of each place). `formulas.test.ts` draws every formula in them and cuts the longest ones at every 11th character, and `reviewed.test.ts` holds the examples the reviews of the change found and three properties, on the examples, on the recorded texts and on cuts of them: the code the parser finds in a text is the same after preprocessing, a price is never maths or a placeholder, and a repair only adds formulas, so every formula the parser finds and KaTeX draws is still there with the same content. The exceptions are the price the parser paired with the next dollar sign, prose it paired between two formulas, a formula rewritten on purpose (Markdown bold, a corrupted escape) and a block still being written.

### Concept maps

A concept map belongs to a subject, and optionally to one topic of an exam (`src/core/maps/`). Every map request names a topic (`topicId`, with or without its `planId`) or a subject alone (`subjectId`), and `mapScope` turns that into the row it means; a topic's exam and subject come from the topic. A topic map is built from the topic's passages, read in parts of at most 24 passages and 18,000 characters. The parts of one request join into a single map (`merge.ts`): its root is the topic's name, and each part's root becomes a main branch under it. The prompt tells the model the topic's title and which part of how many it is reading, and has it label the root of each part with a short name of its own for what that part covers. A part root that repeats the title (ignoring case and the spaces around it) folds into the map's root, parts that return the same root label share one branch, and a concept two parts name alike is kept once, with the sources of both. Each finished part waits in the job's params until the last one is read, so a resumed or retried build reads only the parts it has not read, and no half-built map shows. A map holds up to 2,000 concepts (`MAP_LIMITS`); a map of more than 25 opens with everything below its main branches folded. The view moves on its own (when the map opens and after an unfold) only down to a zoom of 0.85 (`MIN_READ_ZOOM`), which keeps a concept's label at 11 px or more on screen at every text size. The opening view shows the whole visible map when it fits at that zoom, else the root and its nearest branches, and an unfold puts the branch's parent and first children on screen and leaves the rest to scrolling. The student can still zoom out by hand, and the Adatta la mappa button shows the whole visible map centred at any zoom down to the canvas's own smallest, 0.15 (`fitViewport`, `CANVAS_MIN_ZOOM`), so it only stops short for a map that does not fit even then. The Nuova mappa dialog opens the map page with `build` in the navigation state, and the page starts the build once it has found no map and no build for the scope. The dialog also lets the student say how they want the map (up to `MAP_INSTRUCTION_MAX`, 2,000 characters, as for `maps.edit`). `maps.generate` takes it as `instruction`, trimmed, and an empty one is none. It is kept in the job's params, so a retry or resume sends it again, goes to every part's call as `instruction`, and is stored in the map's own JSON (`StoredMap.instruction`, no column), where the Mappe tiles and the switcher beside the map's title show it. The prompt (`map.generate`, version 6) takes it as guidance about focus and style that never overrides grounding, the schema or the content language. With one a map need not cite every passage and may be as small as two concepts, and a part that holds nothing for the request answers `{"result": {"kind": "nothing"}}` instead of a map (a request without an instruction keeps the plain schema, at least eight concepts per part). Such parts are done like the others, so a resume or retry does not read them again, and they stay out when the parts join. When every part is empty no map is stored and the build fails with `map-nothing-matched`, which the map page shows with the request in a field the student can change. That error is in `EMPTY_RESULT_ERRORS` (`src/shared/ipc.ts`), so Attività lists the build with the jobs that ended today, not as a problem, and its row opens the map page on that build: the navigation state carries the job's id, since a scope can have several such requests, and the page shows that request's words in the field even when the scope already has maps (the switcher beside the title then lists them, also when there is only one). The id stays in that history entry, so a reload or Back and Forward return to the request, and a request whose job is gone, or anything the student does on the page, takes it out. A request without an instruction gets the scope's map or its build as before. A request with one is a map of its own: a finished build does not answer it, so the map is added next to the others, and only a build that is queued or running for the same scope and the same instruction is the same request (`enqueueMaps`). While such a map builds, the page shows its working state in place of the maps already there and opens the new map when it is done. The page reads the build it waits for by job id (`maps.build` takes the `jobId` that `maps.generate` returned, and falls back to the scope's newest build when the page opened without a request), and opens the map by the `mapId` the finished build returns, since two builds of one scope can finish in either order. A whole-subject map is one map from one call: up to 24 passages of the subject's sources, each cut to 750 characters (`subject-sources.ts`). Those sources are the subject's files in linked folders, the material imported with the subject and the study material of the subject's exams, at their newest version. Hidden copies, files gone from their folder, sources still being read and past exam papers that none of the subject's exams studies from stay out. The first passage of each section goes first, spread evenly from the first section to the last when there are more than fit, and the rest is filled evenly from the other passages. Core reads the ids of all the subject's passages and the text of the chosen ones only. The model writes in the profile's content language, since no exam sets one. `maps.rename` gives one map a name of its own, which may repeat another map's, and keeps its request. `maps.delete` removes one map, with its undo history, and the row goes with its scope's last map. It also stops every build that writes that map (`Runner.discard`, which cancels the job and drops it from Attività so nothing offers to resume it), and a running build checks its signal right before it stores the map, so a build that ends later never brings it back. A map still being written has no id on the page yet, so the page names it by its build's `jobId`. A plain request whose finished build made a map that was deleted since starts a new build. Flashcards made from a map belong to the subject and stay, and a link to a deleted map (`?map=` in the address) lands on Mappe, which says the map was deleted.

The map page lives at `/maps/:subjectId` for a whole subject and `/maps/:subjectId/:topicId` for a topic. The older `/plans/:planId/map/:topicId` opens the same page, for links made before and for a topic whose exam has no subject. A concept's source opens in a side panel on the map page, at the passage it cites, with the same viewer the Library's drawer uses (`useSourceView` in `SourceViewer.tsx`); the canvas narrows beside it.

### Open gaps

`plans.openGaps` (`src/core/study/openGaps.ts`) lists an exam's open gaps for its page: each with its topic's name, its sentence as stored, how many wrong answers are linked to it, and a level of `serious`, `moderate` or `minor`. It returns at most 100 gaps and `total`, the number of open gaps. The number of gaps `plans.recommend` counts per topic and the length of this list come from one rule, `OPEN_GAPS_WHERE` in `plans/progress.ts`: not closed, on a topic still in the exam. `planSeries` and the list rank through one function, `rankedOpenGaps`, so the two cannot drift apart; the list refines the order with the level. The page's own state (how many rows are shown, the working mark while an analysis runs) belongs to the renderer.

The exam page lists them in `GapsSection`, which reads the list again each time the page opens. "Colma" opens `/plans/:planId/gap/:gapId` (`GapPage`), which starts the drill of that gap through `useGapDrill`, the hook the path's "Rivedi gli errori" uses too, and replaces its own history entry with the drill's quiz (`/plans/:planId/quiz/:topicId?attempt=…&gap=…`) once the attempt is ready. That quiz keeps the page's title and line and shows the gap above the drill's explanation. A drill asks `GAP_DRILL_QUESTIONS` questions (`src/shared/gap-drill.ts`) and a gap closes by `shouldClose` (`src/core/study/gaps.ts`): right answers in two sessions on different days. The end of the drill reads `plans.gapState`, which says whether the gap that counts is closed. A gap can leave the open list without being closed: when the analysis finds it is the same idea as another (`merged_into`), it counts for the gap that absorbed it, so `gapState` follows the merges to the last gap and reports that one, and the end says "closed" only when that gap is. The read syncs the exam's gaps first, since that is what closes a gap whose answers are right. The page reads its drill by the id of the job it started (`study.gapDrillRead` with `jobId`), so a merge while the drill is written does not hide it; a read by gap follows the merge too.

## Build and tests

Electron Vite builds main, preload, core and renderer entries into `out/`. Only the shell and the exam list are in the renderer's entry chunk; every other page loads on its first visit, and the previous page stays on screen until it has. A page with tabs or an optional id is therefore one route (`plans/:planId/:view?`), so its tabs switch without a load, and a redirect is a route loader rather than a rendered `<Navigate>`, which would cancel a navigation still loading its page. A stylesheet goes with the component that uses it, since a page's CSS now loads only with that page. Main and core load the HTML parsers (linkedom, Readability, Turndown) and mammoth on the first import that needs them. `electron-builder.yml` packages native libraries outside ASAR and chooses DMG/ZIP, NSIS or AppImage/deb. `scripts/test-electron.mjs` runs Vitest with Electron's Node ABI. Native Playwright tests launch temporary Electron profiles, rather than the owner's current workspace.

## Restore safety

Restore validates SQLite integrity and foreign-key references before and after migrations. Future schema versions and unexpected ZIP paths are rejected before live data moves. Only canonical hash-named blob files and their metadata accompany the database; restore verifies their hashes and metadata. Existing runtime/model caches are copied into staging and survive both commit and rollback. A fsynced sibling restore journal records the original and staged directory identities. Startup checks that journal before creating workspace folders.

The app keeps the original `.old` workspace until the restored core reports healthy readiness. The archive worker validates the promoted database, then commits and cleans up the swap, so this work stays off the main window thread. A commit that fails (a full disk, or a journal file Windows keeps locked) is tried twice more. After that, main stops core and tries once more, since a stopped core has let go of its files. If that fails too, main rolls back to the original at once, and Settings says the data from before the restore is back. If core won't stop or the rollback fails, core stays stopped, no backup, restore, move or wipe can start, and Settings asks the student to reopen Pyxis so startup recovery can finish. Core never keeps running on a promoted copy that the next launch would roll back and delete. An interrupted uncommitted swap rolls back to that original. Commitment is recorded before deleting old data; a failed cleanup leaves the committed marker for the next startup and never selects a partly deleted original. A replaced or unexpected directory stops recovery with both copies preserved for inspection.
